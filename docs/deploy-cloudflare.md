# Выкладывание на Cloudflare

Порядок, а не список: каждый следующий шаг опирается на предыдущий, и половина
шагов — действия в панелях, которые из сессии не делаются. Что делается из
сессии, помечено «я».

Приложение к этому моменту уже работает под workerd: порт проверен на стенде,
оба обхода браузером зелёные. Остальное — ресурсы на аккаунтах.

---

## 1. База

**Вы.** Создать проект Supabase. Регион — **eu-central-1 (Франкфурт)**: для
Бишкека он примерно вдвое ближе Токио, а Hyperdrive этого не отменяет — он
держит пул у края сети, но каждый незакэшированный запрос всё равно идёт до
региона базы. Пароль базы придумываете вы; мне он не нужен и знать его я не
должен.

**Я.** Применить миграции и зарегистрировать плановые работы:

```bash
NODE_USE_ENV_PROXY=1 SUPABASE_PROJECT_REF=<ref> node db/push-hosted.mjs --check
```

```bash
NODE_USE_ENV_PROXY=1 SUPABASE_PROJECT_REF=<ref> node db/push-hosted.mjs --apply --schedule
```

Скрипт ходит через Management API, а не psql: строка подключения к базе —
секрет, которому нельзя лежать ни в репозитории, ни в переменных окружения
сессии. Токен Management API хранится сетевым секретом окружения и
подставляется прокси в заголовок.

На чистом проекте `--reset` не нужен. Он есть для случая, когда в проекте
лежит чужая схема, и сносит схемы `public` и `app` целиком — схемы платформы
(`auth`, `storage`, `realtime`, `extensions`, `vault`) не трогает.

**Вы.** Если `--schedule` пожалуется на pg_cron: Dashboard → Database →
Extensions → включить `pg_cron`. Без расписания инварианты 1, 12 и 14 держатся
только на словах: мандаты не истекают сами, уведомления не ставятся в очередь,
просроченные закрепления не снимаются.

Проверить, что работа идёт:

```sql
select job, status, silence from maintenance_health_v;
```

## 2. Hyperdrive

**Вы.** Cloudflare → Storage & Databases → Hyperdrive → создать конфигурацию.
Строка подключения — **Direct connection** из Supabase (Settings → Database),
**не** пулер. Hyperdrive сам пулер, и два пулера друг за другом ломают
`set local`, на котором держатся понижение роли и клеймы входа: один агент
увидел бы данные другого, и RLS бы не помогла. Строку вставляете в панель
Cloudflare, в чат она не идёт.

Из панели нужен только **идентификатор конфигурации** — он не секрет.

**Я.** Раскомментировать привязку в `web/cloudflare.config.ts` и подставить
идентификатор. Образец уже лежит там.

## 3. R2

**Вы.** Включить R2 в панели Cloudflare. На момент написания API отвечает
`10042 Please enable R2 through the Cloudflare Dashboard`, и аккаунт у вас
один, так что включение просто не доведено до конца — даже на бесплатном
тарифе Cloudflare требует привязанный способ оплаты.

**Я.** Создать бакет `liberterra-photos`. Привязка в конфиге уже есть.

Бакет остаётся **закрытым**: публичный доступ не включается никогда. Байты
отдаёт приложение, право на файл проверяется в базе на каждый запрос
(инвариант 11). Публичный адрес у файла обошёл бы эту проверку молча. Отсюда
цена: исходящий трафик фотографий платит Cloudflare Workers, а не R2.
Сознательный размен на то, что снятый с публикации объект перестаёт отдаваться
в ту же секунду.

## 4. Секреты воркера

**Я.** Список того, что воркеру нужно, лежит в `web/cloudflare.config.ts` —
там он объявлен через `bindings.secret()`, то есть воркер, которому не хватает
переменной, ругается при запуске, а не отдаёт наполовину работающий сайт.

Значения:

| переменная | откуда |
| --- | --- |
| `DATABASE_URL` | не нужна, когда настроен Hyperdrive |
| `SESSION_SECRET` | придумать длинную случайную строку |
| `CATALOG_DB_ROLE` | `anon` |
| `AUTH_DB_ROLE` | `auth_service` |
| `CABINET_DB_ROLE` | `authenticated` |
| `NOTIFY_DB_ROLE` | `notifier` |
| `SITE_URL` | адрес сайта: он уходит в ссылки собственникам |
| `OTP_TRANSPORT` | `dev`, `smtp` или `whatsapp` — но смотрите раздел «Вход» ниже |
| `NOTIFY_TRANSPORT` | `dev`, `telegram` или `whatsapp` |
| `PHOTO_STORAGE` | `r2` |

`PHOTO_DIR` воркеру не нужна намеренно: драйвер диска там не работает и
работать не должен.

## 5. Вход: открытое решение, без которого кабинет публиковать нельзя

Вход в кабинет — по коду на адрес почты. Отправки почты **пока нет**:
`web/lib/mail.ts` — умышленная заглушка, и в ней написано почему. Ставить
почтовую библиотеку до выбора провайдера значит выбрать его молча, а это
решение владельца: домен, обратный адрес, деньги.

Поэтому работает только `OTP_TRANSPORT=dev`, а он **показывает код прямо на
экране**. На стенде это удобство. В публичном вебе это открытая дверь: любой
введёт чужой адрес и прочитает код входа. **Кабинет с `OTP_TRANSPORT=dev`
публиковать нельзя.**

Выходов два, и оба требуют решения:

- выбрать провайдера почты и добавить в `lib/mail.ts` ветку отправки. На
  Cloudflare это должен быть провайдер с **HTTP API** (Resend, Postmark,
  SendGrid): воркер не умеет исходящий SMTP, так что `OTP_TRANSPORT=smtp`
  там не заработает даже после установки библиотеки. Ветка под HTTP API в
  файле предусмотрена заранее;
- либо выложить пока только публичный каталог, а кабинет закрыть — например
  правилом Cloudflare Access на `/cabinet/*`.

Что нужно от провайдера, чтобы письмо с кодом доходило, а не падало в спам,
перечислено в шапке `web/lib/mail.ts`: свой домен с записями SPF и DKIM,
читаемый обратный адрес, отправка не из личного ящика сотрудника.

## 6. Первый администратор

В базе ноль агентов, а новый агент требует одобрения администратором — то
есть одобрять некому. Это не упущение: инвариант 17 умышленно не даёт агенту
повысить себя, и защищён он тремя слоями (права на столбцы, триггер, правило
«последний администратор»).

Разрыв закрывается там, где он и предусмотрен: триггер пропускает смену роли,
когда `auth.uid()` пуст, то есть для владельца базы. В шапке миграции 0021 это
написано прямо.

Строка создаётся заранее, до первого входа: `app.login_by_email` делает
`on conflict (email) do update` и роль со статусом **не трогает**, поэтому
первый вход подхватит готового администратора, а не создаст нового агента в
ожидании одобрения.

**Я.** Одним запросом, когда вы назовёте адрес:

```sql
insert into agents (email, full_name, role, status)
values ('<адрес>', '<имя>', 'admin', 'approved');
```

Агентство подставится по умолчанию — «Liberterra» уже создано миграцией 0042.

## Что остаётся после

Фотографии переносить не нужно: в размещённой базе их нет. Если появятся —
`web/scripts/photos-to-storage.mjs` переносит по ключам из базы, а не обходом
каталога, и повторный запуск безопасен.

Vercel. Проект `liberterra` собирает соседнюю ветвь, и его последняя
production-сборка в ошибке. Пока он жив, у продукта два выкладывания из разных
ветвей; решать это надо явно, а не оставлять как есть.

Две гарантии проверяются только на выложенном воркере, и до тех пор про них
честно сказать лишь то, что они запрошены:

- обрезка, качество и выброс метаданных у картинок. `vite dev` поднимает
  упрощённую Images, которая понимает только `width`, `height`, `rotate` и
  `format`;
- «`set local` переживает транзакционное пулирование». Местный Hyperdrive не
  пулит так, как настоящий. Утверждение верно по построению — всё, что
  выставляется, выставляется внутри одной транзакции, — но это не то же самое,
  что проверено.

Первое, что надо посмотреть после выкладывания: загрузить фотографию и
сравнить её размер и метаданные с тем, что обещано, и войти двумя агентами
подряд, убедившись, что второй видит своё.
