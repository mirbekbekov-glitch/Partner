# Веб: публичный каталог и кабинет агента

Next.js 16, App Router. Два приложения на одной базе и одном стеке:

- **каталог** — открыт всем, читает базу под ролью `anon`;
- **кабинет** — для агентов, читает и пишет под ролью `authenticated` с
  клеймами вошедшего;
- **вход** — отдельная роль `auth_service`, которой открыты ровно две функции.

## Почему роли, а не проверки в коде

Каждая транзакция понижает права до роли, у которой физически нет доступа к
лишнему. Каталог не достанет контакт, даже если запрос к нему написан
неправильно: у роли `anon` нет прав на таблицу `contacts`, а построчные
политики отдают только опубликованные объекты.

То же в кабинете. Здесь нет ни одной проверки «этот ли агент владелец
мандата»: это решают политики и функции базы. Проверка, повторённая в коде
страницы, разошлась бы с базой при первой же правке — и разошлась бы молча.

Поэтому в `app/cabinet/actions.ts` нет ни одного `if (agent.role === …)`.
Задача этого файла — передать ответ базы человеку словами.

## Запуск

```bash
cp .env.example .env
```

Заполнить `SESSION_SECRET` (это ключ подписи сессии, без него вход
подделывается тривиально):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Дальше:

```bash
npm install && npm run dev
```

Данные для разработки — `db/dev_seed.sql` (каталог) и
`db/dev_seed_cabinet.sql` (обращения и объявления с площадок), фотографии —
`node scripts/make-dev-photos.mjs`.

## Вход

Номер телефона и код в WhatsApp. **Провайдер WhatsApp Business API не
выбран** — это открытое решение владельца продукта, и оно платное: каждое
сообщение с кодом стоит денег.

Поэтому отправка вынесена за одну функцию в `lib/otp.ts`, и до выбора
провайдера работает `OTP_TRANSPORT=dev`: код печатается в журнал сервера и
показывается на странице входа. Так кабинет можно разрабатывать и показывать
целиком, не делая вид, что WhatsApp уже подключён.

Подключение настоящего провайдера — это новая ветка в `sendLoginCode()` и
строка `OTP_TRANSPORT=whatsapp` в окружении. Ничего другого менять не
придётся: сам код, его срок, одноразовость и защита от подбора живут в базе
(инвариант 18) и от провайдера не зависят.

**Сессия своя, а не Supabase Auth.** Причина в том же: код отправляем мы,
значит и подтверждение номера происходит у нас. Из подтверждённого номера
собирается ровно то, что выдал бы Supabase — клеймы `sub` и `phone`, которые
база читает через `auth.uid()` и `auth.jwt()`. Поэтому переход на Supabase
Auth позже меняет только `lib/session.ts`.

Куки подписаны, а не зашифрованы: внутри нет тайн — идентификатор и свой
номер человек и так знает. Подпись нужна, чтобы номер нельзя было подменить
на чужой.

## Что в кабинете есть

| Экран | Что делает |
|---|---|
| `/cabinet` | сводка: свои объекты, срочное, очередь обращений, объявления в работе |
| `/cabinet/objects` | список; подтвердить актуальность, опубликовать, снять |
| `/cabinet/objects/[id]` | карточка: фотографии (загрузка, обложка, порядок, удаление), собственник, подборы, показы, ссылка собственнику |
| `/cabinet/inquiries` | очередь обращений: взять в работу, отказать с причиной |
| `/cabinet/candidates` | объявления с площадок: взять, вернуть, отказаться |
| `/cabinet/agents` | состав агентства; администратору — одобрение, роли, блокировка |
| `/cabinet/scheduler` | здоровье планировщика; администратору — ручной запуск |
| `/cabinet/profile` | своё имя; номер меняется подтверждением, а не правкой поля |

Три состояния входа, и все три названы словами: входа нет, вход есть и агент
ждёт одобрения, вход есть и агент работает. Пустой список и «нет доступа» для
человека выглядят одинаково, поэтому второе говорится прямо.

## Фотографии

Присланный браузером файл в хранилище не попадает: он расшифровывается и
кодируется заново в webp. Это одно решение закрывает четыре вещи — EXIF с
координатами съёмки, файл, который не является изображением, вес снимка с
телефона и разнобой форматов. Ключ файла выдаёт сервер; имя из браузера не
участвует.

Фотографии кабинету отдаёт `/cabinet/photo/…`, а не публичный адрес:
публичная отдача смотрит в `public_photo_v`, где лежат фотографии только
опубликованных объектов, — а загружают их до публикации.

Хранилище — каталог на диске (`PHOTO_DIR`). Supabase Storage не подключён;
когда дойдут руки, меняются только `save` и `remove` в `lib/photos.ts`.

## Чего в кабинете нет

Создания объекта и экрана подбора. Серверная часть готова
(`object_matches_v`, `create_match()`, `schedule_showing()`), экранов к ней
ещё нет.

## Клиентский код

Один компонент: `app/cabinet/ActionForm.tsx`. Он нужен, чтобы ответ базы
показывался рядом с кнопкой, которую нажали. Остальное — серверные
компоненты без клиентского JavaScript.

Исключение — действия, после которых строка меняет вид (одобрение агента,
смена роли). Там успех уходит в адрес страницы и показывается сверху:
иначе форма с сообщением исчезает вместе с кнопкой, и действие срабатывает
молча.

## Проверки

```bash
npm run typecheck
```

```bash
npm run smoke
```

```bash
npm run smoke:cabinet
```

```bash
npm run smoke:photos
```

`smoke` доказывает, что каталог действительно работает под ролью `anon`:
контакты, мандаты, комиссия и пул кандидатов ему недоступны, а запись
запрещена дважды — правами роли и транзакцией только для чтения.

`smoke:cabinet` проверяет вход и понижение прав кабинета: что клеймы не
протекают между запросами по одному соединению из пула (самая опасная ошибка
этого слоя), что агент не выдаёт себе прав, и что труба входа работает —
выдача кода, отказ неверному, одноразовость.

`smoke:photos` проверяет три обещания, которые экран дать не может: в
хранилище попадает файл, созданный нами; координаты съёмки из снимка не
уезжают в каталог; файл, не разбирающийся как изображение, не попадает
никуда. Все три держатся на одном решении — перекодировании, — и потому
ломаются вместе.

Ни одна из них не проверяет вёрстку. Вёрстку проверяют глазами, и для этого
есть проходы браузером:

```bash
npm run walk
```

```bash
npm run walk:photos
```

Они ничего не утверждают и в тесты не входят: проходят кабинет насквозь и
делают снимки. Половина правок в кабинете родилась оттуда.
