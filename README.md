# Платформа профессионалов — модель данных и серверные инварианты

Платформа аренды и продажи недвижимости в Бишкеке. Публичный каталог открыт
всем, CRM живёт внутри кабинета агента и открывается только агентам со
статусом «одобрен». Сайт и CRM — один продукт и одна база: **публикация
объекта это его состояние, а не выгрузка во вторую систему.**

Этот этап закрывает модель данных и серверные инварианты. UI минимальный.

## Состояние репозитория

Репозиторий был пуст, поэтому проект создан с нуля. Готово и проверено:
схема, инварианты, слой доступа, тесты и минимальный UI кабинета
(Next.js App Router + Supabase).

### Проверка перед развёртыванием

```bash
./db/preflight.sh
```

Локально миграции применяются суперпользователем, а он обходит проверки
прав — поэтому обычный прогон **не видит** зависимостей от привилегий,
которых на Supabase нет. Эта проверка применяет миграции ролью без прав
суперпользователя на базу, где схема `auth` создана не нами и `auth.users`
принадлежит другой роли.

Она уже нашла одну такую зависимость: `app.ensure_agent()` читала
`auth.users` и падала с `permission denied for table users`. Теперь почта
берётся из токена через `auth.jwt()`, а чтение таблицы осталось запасным
путём с перехватом исключения. Проверка отзывает все права на `auth.users`
и логинится заново — вход обязан работать.

Совместимость с CLI тоже проверена: `supabase db push --dry-run` принимает
нумерацию `0001_…` и перечисляет все 26 миграций в правильном порядке,
переименовывать файлы не нужно.

### Развёртывание на Supabase

Одной командой, если есть доступы:

```bash
SUPABASE_ACCESS_TOKEN=... SUPABASE_PROJECT_REF=... SUPABASE_DB_URL=... \
  SITE_URL=http://localhost:3000 ./db/deploy.sh
```

Скрипт применяет миграции и сам прописывает Redirect URLs через
Management API. Шаблон письма он не трогает: на бесплатном тарифе это
запрещено, а штатному входу шаблон и не нужен — см. ниже. Список проектов:
`./db/deploy.sh --list`.

Где взять: токен — `supabase.com/dashboard/account/tokens`, строка
подключения и пароль базы — Project Settings → Database, URL и anon key —
Project Settings → API.

**Без доступов** то же самое делается руками: вставить `db/bundle.sql`
(все миграции одним файлом) в SQL Editor панели, затем сделать две
настройки ниже.

### Где это работает

Боевой адрес: **https://liberterra-nine.vercel.app**

Развёрнуто на Vercel, проект `liberterra`, тариф Hobby. Привязки к GitHub
нет: Vercel не смог связаться с репозиторием («You need to add a Login
Connection to your GitHub account first»), поэтому исходники выложены через
его API напрямую. Следствие: **пуш в репозиторий сам по себе ничего не
выкатывает**. Чтобы включить автодеплой, нужно один раз связать GitHub в
настройках Vercel, после чего проект подхватит ветку.

Переменные окружения заведены в проекте: адрес и анонимный ключ Supabase —
обычные, `SUPABASE_SERVICE_ROLE_KEY` и `CRON_SECRET` — секретные.

Вход по почте настроен на этот адрес: `site_url` и Redirect URLs в Supabase
указывают на него, а `http://localhost:3000` оставлен для разработки.

Первого администратора система себе назначить не может — это правило из
`0011`, агент не вправе повысить себя. После первого входа роль выдаётся
запросом к базе.

### Публичный каталог

Открытая часть — `/` и `/objects/<id>`. Читает **только** представление
`public_catalog_v`, в котором нет ни комиссии, ни агента, ни собственника,
ни контактов, и которое отдаёт лишь объекты в состоянии `published`.

Это не вежливость страницы, а устройство: правило «публичная часть читает
только витрину» проверяется `tests/check-public.sh` и входит в общий прогон.
Прямое обращение к `objects` со страницы каталога валит сборку тестов —
и правильно: анониму та таблица открыта политикой каталога, а среди её
колонок есть `created_by_agent_id`.

Проверено на живых данных анонимом, без единой cookie: в исходнике страницы
нет ни имён агентов, ни собственника, ни телефонов, ни слова «комиссия»,
а черновой объект по прямой ссылке отдаёт 404, а не устаревшую цену.

Фильтры живут в строке запроса, поэтому ссылкой на подборку можно делиться
и её же видит робот поисковика. Каталог индексируется, кабинет и вход
закрыты `noindex` каждый сам за себя: общий запрет в корневом макете закрыл
бы заодно и каталог.

Поиск разбивается на слова, и каждое должно найтись в адресе или районе.
Кыргызские буквы ищутся в обоих написаниях: «чуй» находит «Чүй». Значения
берутся в кавычки — без этого запятая в запросе («Чүй, кв») роняла весь
запрос в `failed to parse logic tree`, и человек видел пустой каталог.

### Агентство недвижимости

Агент либо состоит в агентстве («Этажи» и подобные), либо работает сам.
Принадлежность он указывает при регистрации, на том же экране, где вписывает
имя.

Два правила, из которых следует остальное.

**Название уникально по нормализованному виду.** Иначе «Этажи», «этажи» и
«ЭТАЖИ» станут тремя агентствами, фильтр по источнику развалится, а сводить
их придётся руками. Тот же приём, что у телефонов контактов: ограничение,
которое обходится форматированием, хуже отсутствующего.

**Агент заявляет агентство, но не подтверждает его.** Иначе любой впишет
«Этажи» и прикроется чужой репутацией. Поэтому у связи есть отдельный
признак `org_confirmed`, и поднять его может только админ — правило держит
триггер, а не проверка внутри функции. Снять подтверждение может и сам
агент, сменив место работы: это не повышение прав. До подтверждения рядом с
названием в списке агентов стоит пометка «не подтверждено».

**Частный агент — это отсутствие организации**, а не агентство с названием
«Частный агент». Иначе такие агенты склеились бы в одно несуществующее
агентство.

### Чьи это объекты: источник в CRM

В списке объектов кабинета есть фильтр источника: мои, моего агентства,
других агентств или конкретный агент. Ответственным считается listing-агент
активного мандата, а у черновика без мандата — тот, кто его завёл: иначе
такие объекты выпадали бы из любого фильтра.

**В публичном каталоге этой возможности нет и не будет.** Каталогом
пользуются не только агенты, и внутреннее устройство агентства их не
касается: `public_catalog_v` не содержит ни агента, ни агентства, ни
собственника, ни комиссии. Это не договорённость, а проверка — состав
витрины сверяется в `inv9_public_api`, и попытка добавить туда колонку
«ведёт» роняет прогон.

### Заявка с сайта

Под карточкой объекта — форма: имя, телефон, вопрос. Это **единственная
запись в базу от неизвестного**: до неё писать могли только одобренные
агенты. Поэтому поверхность сведена к одной функции `submit_lead()`, а
таблица заявок анониму не выдана вовсе — ни на чтение, ни на запись.

Проверки живут в базе, а не в форме: форму обойти тривиально, запрос уходит
прямо в PostgREST.

| | |
|---|---|
| объект | только опубликованный; на черновик и на несуществующий — один и тот же ответ, чтобы существование черновика не выяснялось перебором |
| имя | 1–120 символов |
| сообщение | до 2000 символов |
| телефон | нормализуется так же, как у контактов: `+996700112233` и `0700 11 22 33` — один номер |
| повтор | та же пара «телефон + объект» за сутки возвращает прежнюю заявку: человек нажал дважды, агент не должен звонить дважды |
| частота | не больше 5 заявок с номера в час и 30 на объект в час |
| бот | в форме скрытое поле-приманка; заполнено — ответ как при успехе, но в базу ничего не идёт |

Телефон заявителя — такой же чувствительный, как телефон собственника, и
живёт по тому же правилу: видит тот, кто ведёт объект, и админ. Предикат
взят тот же, что у правки объекта, — иначе вышло бы, что снять объект с
публикации агент не может, а читать телефоны его заявителей может.

По заявке заводится задача тому, кто ведёт объект, со сроком через два часа
— и дальше её подхватывают обычные напоминания. Заявка, о которой никому не
сказали, бесполезна.

Заявки в кабинете — `/cabinet/leads`: взять в работу, отработана, спам.

Оформление публичной части перенесено из прототипа: поиск отдельной
панелью в герое, сетка карточек, сортировка ссылками, карточка объекта с
прилипающей формой заявки. Шрифт — Manrope из дизайн-системы, поверхности
тёплые нейтральные (`surface-100/200/raised`), шкала отступов 4px.

Фотографии объектов есть не всегда: агент заводит объект с телефона, снимки
добавляет позже. Вместо серого прямоугольника рисуется фасад
(`app/Facade.tsx`), и строится он **из данных самого объекта**: этажность
задаёт высоту, комнаты — число окон, площадь — ширину. Поэтому дома в
каталоге отличаются друг от друга тем же, чем отличаются объекты. Тот же
рисунок подставляется, когда ссылка на фото протухла.

Метки на карточке только те, за которыми есть данные. «Подтверждён сегодня»
считается из `actual_at`, то есть из инварианта 5. Метки «Топ» нет: ей
неоткуда взяться, кроме как из выдумки.

Фирменный цвет — красный `#BE2C28`, взят пипеткой из знака, а не на глаз.
На белом он даёт 5.87 : 1 и годится для обычного текста; на тёмной теме —
только 3.09 : 1, поэтому там свой оттенок того же тона, `#DA524E` (4.57 : 1),
и текст на кнопках становится тёмным: белый на светло-красном дал бы 2.6 : 1.

Из-за этого пришлось развести ошибку и фирменный цвет: раньше ошибка была
красной надписью, а теперь красный — цвет ссылок и кнопок, и одним тоном их
не различить. Ошибка отличается **формой**: плашка с подложкой и полосой
слева, текст темнее фирменного. Все пары проверены по контрасту в браузере,
в обеих темах.

Название агентства — Liberterra. В шапке стоит знак (`public/liberterra.png`),
подписи рядом нет: в самом знаке уже написано «Liberterra», а имя, набранное
дважды, читается как ошибка вёрстки. Название остаётся в `alt` — для тех, кто
слушает страницу, и на случай, если картинка не загрузилась. Иконка вкладки
(`app/icon.png`) вырезана из квадратной части знака.
Заголовок каталога держится отдельно от бренда (`CATALOG_TITLE`): в шапке
стоит имя, а заголовок страницы должен говорить, что на ней лежит.

Телефоны агентства стоят в шапке на каждой публичной странице, все три
сразу: это разные операторы, и человек выбирает тот, что дешевле ему. Живут
в `lib/agency.ts` — одно место на весь сайт. На узком экране номера уходят
на свою строку целиком, а не прячутся за «показать номер»: спрятанный
телефон — это потерянный звонок.

### Настройка Supabase для входа

Вход сделан по ссылке на почту. Нужна **одна** настройка в панели:

**Authentication → URL Configuration → Redirect URLs** — добавить
`http://localhost:3000/auth/callback` и адрес продакшена.

Больше ничего делать не надо: письмо идёт родным шаблоном Supabase.
Его ссылка ведёт на `/auth/v1/verify` самой Supabase, та проверяет токен и
отправляет браузер на наш `/auth/callback` с `?code=`, который обменивается
на сессию (поток PKCE, `@supabase/ssr`). Ссылку надо открывать в том же
браузере, откуда её запросили: `code_verifier` лежит в его cookie.

Второй маршрут, `/auth/confirm`, ждёт `token_hash` и работает только с
переписанным шаблоном письма:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email">Войти в кабинет</a>
```

**Шаблоны писем — платная возможность.** На бесплатном тарифе со стандартным
отправителем Supabase отвечает на попытку их изменить:

> Email template modification is not available for free tier projects using
> the default email provider.

Поэтому рабочий путь по умолчанию — `/auth/callback`, которому шаблон не
нужен вовсе. `/auth/confirm` оставлен: он удобен для проверки входа без
письма (ссылку выдаёт `POST /auth/v1/admin/generate_link`) и пригодится,
если шаблон однажды станет доступен.

Ещё одно ограничение бесплатного тарифа: стандартный отправитель писем
сильно ограничен по частоте. Для настоящей работы нужен свой SMTP — он же
снимает запрет на шаблоны.

### Напоминания о задачах

Рассылку запускает `/api/cron/reminders` по расписанию из `vercel.json`.

**Раз в сутки, в 9:07, а не ежечасно** — это ограничение тарифа Hobby на
Vercel: там запуск по расписанию разрешён один раз в день, и с ежечасным
расписанием деплой просто не проходит. На платном тарифе достаточно вернуть
`"schedule": "7 * * * *"` — код рассылки от этого не зависит, он идемпотентен
и рассчитан на любую частоту.

Следствие, о котором стоит знать: напоминание о задаче придёт в ближайший
запуск, то есть в худшем случае почти через сутки. Нужны три переменные: `CRON_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`
и `TELEGRAM_BOT_TOKEN` — см. `.env.example`.

**Отправка не проверена на живом Telegram.** Токена бота здесь не было, да и
посылать сообщения в реальный чат без спроса не следует. Проверено всё до
границы HTTP: что и кому напоминать, идемпотентность, отмена при выполнении,
защита от двойной отправки, отчёт о неудаче.

Агент без привязанного Telegram получает запись со статусом
«нечем доставить», а не тишину: в списке задач это видно, и профиль
объясняет, что делать. Привязать Telegram может админ —
`set_agent_telegram()`; самостоятельная привязка требует подтверждения через
бота, и она не сделана.

## Инварианты и чем они держатся

Все проверки живут в базе. Это сознательно: PostgREST отдаёт таблицы
напрямую, поэтому проверка в UI защищает только UI.

| № | Инвариант | Механизм | Тест |
|---|---|---|---|
| 1 | Публикация только при активном мандате; не больше одного активного мандата на объект | `mandates_one_active_per_object_idx` (partial unique) + `c_objects_publication_requires_mandate` + `c_channels_require_mandate` + `d_mandate_release_withdraws_object` + `app.expire_mandates()` | `inv1_publication` |
| 2 | Сделка только из подбора; закрытие закрывает мандат и потребность | `deals.match_id NOT NULL` + `b_deal_from_match` + `e_deal_closed` | `inv2_deal_from_match` |
| 3 | Комиссия 50/50; продажа 2%, аренда 50% первого месяца; до закрытия индикативно | `app.commission_total()`, `app.commission_shares()`, `deal_commission_v`, `match_commission_v` | `inv3_commission` |
| 4 | Телефон виден owner_agent, агентам активной сделки, админу | `app.can_see_contact()` + политики на `contacts`, `contact_phones`, `object_ownerships` | `inv4_phone_visibility`, `inv4b_cabinet_views`, `inv4c_page_queries` |

Тесты проверены мутациями: при снятом триггере публикации, при незакрывающемся
мандате, при открытом всем телефоне и при изменяемом `published_at`
соответствующие тесты падают. Суть не в том, что тесты зелёные, а в том, что
они краснеют, когда инвариант сломан.

## Разбор слоя доступа на обход

`docs/ACCESS-AUDIT.md` — запись сквозной проверки: метод, 14 проверенных
путей, пять найденных дыр и чем они закрыты. Два факта, из которых там всё
следует, стоит держать в голове при любой правке:

1. **`SECURITY DEFINER` обходит RLS.** Проверка прав обязана быть внутри
   функции; политика её не подстрахует.
2. **Политика ограничивает строки, а не колонки.** `grant update on t` плюс
   политика «правь свои строки» означает «правь любую колонку своих строк».
   Правило про колонку держит поколоночный грант или триггер.

## Решения, которые стоит знать

**EXECUTE на новую функцию в Postgres по умолчанию выдан PUBLIC.** Поэтому
все 52 функции схемы `app` были вызываемы любым вошедшим агентом, а мои
`grant execute ... to service_role` не ограничивали ничего — доступ и так
был у всех. Измерено: обычный агент вызовом `app.expire_mandates()` погасил
4 мандата и **опустошил каталог** — опубликованных объектов было 3, стало 0.

Закрыто в `0025`: снят дефолтный PUBLIC, права выданы явно (19 функций
агенту вместо 52), и у двух опасных функций появилась проверка внутри — на
случай возврата гранта. Для функций, которые админ может законно запускать
руками, грант открыт роли `authenticated`, а админа от агента отличает
проверка **внутри** функции: роль в Postgres одна на всех вошедших.

**Публичный каталог был сломан для анонимов, и тесты этого не видели.**
Политика `objects_read` вызывала `app.current_agent_id()`, а анониму ни
`USAGE` на схему `app`, ни `EXECUTE` миграциями не выдавались. Анонимное
чтение падало с `permission denied for function current_agent_id`. Тесты
проходили только потому, что **харнесс выдавал анониму права, которых в
продакшене нет** — он делал тестовое окружение свободнее реального и
маскировал настоящие границы.

Лечение не грантом, а разделением политики: условие для анонима больше не
содержит вызова функций вовсе, поэтому каталог не может сломаться из-за
прав на схему `app`. Закреплено тестом, который проверяет, что у анонима
`USAGE` на `app` нет — и каталог всё равно читается.

**Очередь напоминаний, а не отправка на месте.** В Postgres здесь нет ни
`pg_net`, ни `http`, поэтому исходящий запрос из базы сделать нечем. Но
разделение полезно и само по себе: база решает, что и кому напомнить, — это
проверяемо тестами; Next.js отправляет — это нет. Плюс `unique (activity_id,
kind)`, статус `sending` при выдаче и счётчик попыток: расписание может
сработать повторно, маршрут — упасть на середине, и без этого агент получил
бы одно и то же несколько раз.

**Связь объекта с собственником — основание доступа, а не пометка.**
`can_see_contact()` для участников сделки опирается именно на
`object_ownerships`. Измерено: снятие связи при открытой сделке отбирало у
closing-агента телефон собственника — видел 1, стало 0, — **а сделка шла
дальше** в статусе «аванс». Причём сделать это мог другой участник
в одиночку.

Правило поэтому узкое: пока по объекту идёт сделка, он **не может остаться
без собственника**. Добавлять собственников при этом можно свободно — это
только расширяет доступ. Исправить ошибочно указанного собственника
по-прежнему можно: сначала добавить верного, потом снять неверного, и
объект ни на миг не остаётся без стороны. Без сделки объект можно оставить
и без собственника: это записанный лид, и `create_object()` такое допускает.

**Сумма долей по объекту не выходит за единицу.** Было 2.6 — ничто не
держало сто процентов. Это межстрочное правило, поэтому триггер, а не
`CHECK`: `CHECK` видит только свою строку. Пустая доля означает «неизвестна»
и в сумму не идёт.

**Смена роли в собственности — это перенос, а не правка поля.** Роль входит
в составной ключ `(object_id, contact_id, role)`, поэтому наивный `UPDATE`
оставлял бы у человека две роли по одному объекту вместо одной изменённой.
`set_object_ownership()` это скрывает; структурные колонки `object_id` и
`contact_id` закрыты, так что переподвязать связь к другому объекту нельзя —
только снять и завести заново, и тогда оба действия видны в журнале
по отдельности.

**Порядок шагов в `merge_contacts()` — не стиль, а защита от потери данных.**
Ссылки на контакт устроены так:

```
requirements.contact_id      ON DELETE CASCADE   ← удаление уничтожит потребности
contact_phones.contact_id    ON DELETE CASCADE   ← и телефоны
object_ownerships.contact_id ON DELETE RESTRICT  ← удалить не даст вовсе
```

Поэтому лишняя запись удаляется **последней**, когда с неё уже всё снято.
Измерено: если переставить удаление в начало и у записи **нет** связей с
объектами, `RESTRICT` молчит, и потребность исчезает **без единой ошибки** —
было 1, осталось 0. Если связи есть, неправильный порядок упирается в
`RESTRICT`, то есть ловится случайно; поэтому в тестах есть отдельный случай
записи без связей, который проверяет порядок сам по себе.

Обрабатываются и два уникальных индекса: `contact_phones_one_primary_idx`
(один основной номер на контакт) и `object_ownerships_pkey`
(объект + контакт + роль) — если обе записи указаны собственниками одного
объекта в одной роли, лишняя связь убирается, а не обходится.

**Объединять можно только свои записи — обе.** Иначе объединение становится
способом забрать чужого клиента: приписал к своей записи — и он твой,
вместе с телефоном и потребностями. Дубликат на двух агентов сначала
передаётся одному через `transfer_contact()` либо склеивается админом.

При объединении **роли складываются** — в этом и смысл правила «роли это
флаги одной записи». Пустые поля остающейся записи заполняются из
присоединяемой, заметки склеиваются с пометкой, откуда взялось: терять
написанное человеком незачем. Ведущий агент потребности не меняется, поэтому
инвариант `0018` не затронут и подборы двигать не нужно.

**«Один человек — одна запись» теперь действительно держится схемой.**
Это правило из задания, и схема его не держала: проверка показала, что два
контакта с телефоном `+996700111222` уживались свободно, а тот же номер в
виде `0700 11 12 22` давал **третью** запись того же человека.

Второе важнее первого: простой `unique` по тексту телефона обходится
форматированием, и такое ограничение **хуже отсутствующего** — создаёт
уверенность, которой нет. Поэтому есть `app.normalize_phone()`, которая
сводит `+996700111222`, `0700 11 12 22`, `700111222` и
`+996 (700) 11-12-22` к одному значению, генерируемая колонка
`phone_normalized` и глобальный уникальный индекс по ней. Иностранные
номера остаются цифрами: их план нумерации мы не угадываем.

Компромисс: номер, которым реально пользуются двое, придётся записать
одному контакту. На этом правиле держится смысл `roles[]` — роли это флаги
одной записи, а не повод завести вторую.

**Поиск по телефону перед созданием, и что он отдаёт.** Без поиска правило
только наказывало бы за дубликат: агент узнавал бы о существующей записи из
ошибки сохранения. Но здесь сталкиваются два правила — «одна запись»
требует сказать, что контакт есть, а инвариант 4 чужие контакты закрывает.
`find_contact_by_phone()` отдаёт минимум, который решает задачу: факт
существования и **имя коллеги**, у которого контакт. Имя самого контакта и
ссылку — только если инвариант 4 их и так открывает. Агент уже держит этот
номер в руках, он его и ввёл, поэтому узнаёт ровно одно: с человеком
работает такой-то коллега, надо договориться.

**Роль контакта НЕ обязательна, и это осознанно.** Здесь я поставил
ограничение `check (array_length(roles, 1) >= 1)` и оно оказалось неверным
дважды. Во-первых, оно ничего не проверяло: `array_length('{}', 1)` даёт
`NULL`, `NULL >= 1` тоже `NULL`, а `CHECK` при `NULL` считается
выполненным — контакт без ролей проходил беспрепятственно. Во-вторых, его
не должно быть и в рабочем виде: «контактное лицо» и «доверенное лицо» это
роли **связи** (`object_ownerships.role`), а не контакта, и человек, который
всего лишь контактное лицо по объекту, ни одной роли контакта не имеет.
Запрет закрыл бы случай из самого задания. В списке такой контакт помечен
как «роль не указана».

**Телефоны вынесены в отдельную таблицу `contact_phones`.** RLS в Postgres
построчный, не поколоночный. Телефон в `contacts.phones[]` невозможно
закрыть, оставив контакт открытым: политика либо отдаёт строку целиком, либо
не отдаёт. Это несущая конструкция инварианта 4, а не декоративное разбиение.

**`object_ownerships` закрыта тем же предикатом, что контакты.** Иначе
инвариант 4 обходился бы одним join: таблица связи выдала бы `contact_id`.

**Представления кабинета не присоединяют контакты внутренним join-ом.**
В карточках это LEFT JOIN, в списках — подзапрос. Агент, которому контакт
не положен, видит строку с пустым именем, а не теряет её целиком. Это ровно
«объект, условия и комиссия да, контакт нет».

Цена ошибки здесь измерена: если в `object_list_v` заменить подзапрос
собственников на обычный join, посторонний агент видит **0 объектов из 3** —
RLS скрывает контакты, и внутреннее соединение выбрасывает строки целиком.
Это проверяется мутацией в `inv11_list_views`. Подзапрос нужен ещё и потому,
что у объекта бывает несколько собственников, и join размножил бы строку
объекта.

**Передача клиента переносит работу целиком, а не одну колонку.** Переезжают
контакт, его открытые потребности и подборы по ним. Это следствие инварианта,
а не удобство: `0018` сделала `matches.closing_agent_id` производным от
агента потребности, и проверка показала, что если передвинуть
`requirements.agent_id`, не двинув подборы, инвариант остаётся нарушенным на
существующих строках — триггер на `matches` при правке `requirements` не
срабатывает, и расхождение живёт молча.

Закрытые потребности и отвал остаются за тем, кто их вёл: это уже сделанная
работа, и подборы по ним тоже не двигаются, поэтому инвариант на них цел.

**Передача отказывает при незавершённых сделках**, называя объекты, которые
мешают. Тоже следствие, а не осторожность: агенты сделки заморожены в её
строке, и если подбор уедет к другому, `check_deal_from_match()` перестанет
пропускать правки — проверено, `close_deal()` падал с `INVARIANT_3`, сделка
становилась незакрываемой. Комиссия по идущей сделке принадлежит тем, кто её
ведёт, поэтому передача её не переписывает.

**Передача объекта двигает и listing-агента активного мандата**, то есть
долю listing в комиссии: по инварианту 3 она идёт из мандата.

**«В сделке» означает существующую сделку.** Статус подбора `in_deal` можно
было поставить прямым запросом при нуле сделок: политика `matches_update`
разрешает правку closing-агенту, а PostgREST отдаёт таблицу напрямую. Подбор
начинал врать — заявлял сделку, которой нет, и в списке сделок её не было.
Держит триггер `c_match_in_deal_requires_deal`, а не проверка в функции,
именно потому, что прямой `PATCH /matches` функцию не трогает. Обратное
правило там же: пока сделка жива, подбор из `in_deal` не уводят, иначе
сделка висела бы на подборе, который её отрицает.

Отказ требует причины, показ — даты: «назначен показ» без даты это не
назначенный показ. При выходе из отказа причина очищается — она относилась
к прошлому решению.

**SECURITY DEFINER обходит RLS, поэтому проверка прав обязана быть внутри
функции.** Функции из `0007` были объявлены `SECURITY DEFINER` без
собственных проверок, и на схеме до `0016` посторонний агент мог:

| Что мог сделать посторонний агент | Последствие |
|---|---|
| `close_deal(чужая сделка, любая цена)` | Закрыть чужую сделку и зафиксировать комиссию. Проверено: закрыл по цене 999 000, записана комиссия 19 980, мандат и потребность закрыты |
| `withdraw_object(чужой объект)` | Снять чужой объект с публикации |
| `create_match(объект, чужая потребность)` | Назначить **себя** closing-агентом на чужого клиента — захват половины комиссии |

Политики RLS от этого не защищали и не могли: `SECURITY DEFINER` их обходит
by design. Третий пункт исправлен не проверкой, а изменением логики:
`closing_agent` теперь берётся **из потребности**, а не из того, кто нажал.
Предлагать объект чужому клиенту по-прежнему можно и это полезно, но доля
closing-агента идёт тому, кто ведёт клиента (инвариант 3). Все три случая
закрыты регрессией в `inv13_deal_access`.

**Заключить договор может любой агент, если активного нет.** Здесь я сначала
поставил проверку «только тот, кто завёл объект», и она оказалась неверной:
объект в базу внёс один агент, а договор с собственником есть у другого — при
строгой проверке второй не может его оформить, и объект остаётся
непубликуемым. Заключение договора это принесённая работа, а не действие над
чужой. Остаточный риск признаю: агент может оформить договор на чужой объект
и получить половину комиссии. Он виден в журнале и обратим админом, а запрет
ломал бы честный случай каждый раз. Публикация, снятие и подтверждение
актуальности остаются строгими — это действия над объектом, который уже
кому-то принадлежит.

**Этапы сделки и её завершение — разные функции.** `set_deal_status()` водит
сделку по этапам аванс → документы → подписание → расчёт, но `closed` и
`failed` отклоняет: закрытие требует финальной цены, от которой считается и
фиксируется комиссия, а срыв — причины. Иначе сделку можно было бы «закрыть»
без цены, и комиссия осталась бы непосчитанной.

**Объект, собственник и мандат создаются одной транзакцией** —
`create_object()`. Объект без мандата опубликовать нельзя (инвариант 1),
поэтому цепочка «создали объект, потом мандат, потом связь с собственником»
на любой оборванной середине оставляет объект, с которым нельзя работать.
Проверяется тестом: при мандате с истёкшим сроком не остаётся ни объекта,
ни осиротевшего контакта собственника.

Объект всегда создаётся **черновиком**. Публикация — отдельный шаг, и он
требует мандата; форма это прямо говорит и позволяет завести объект без
договора сознательно.

**Править объект может тот, кто его завёл, listing-агент активного мандата
и админ.** В `0006` это мог любой одобренный агент — политика проверяла
только `app.current_agent_id() is not null`. Пока правки шли через SQL, это
было терпимо; с появлением формы это значило бы, что любой агент молча
переписывает цены и фото в чужих объектах. РЕШЕНИЕ ОБРАТИМО: если в
агентстве правят объекты сообща, политику можно вернуть к прежнему виду.

Защита в два слоя, и это не избыточность: `update_object()` проверяет право
сама, но PostgREST отдаёт таблицы напрямую, поэтому агент может послать
`PATCH /objects` мимо функции — там держит политика. Тесты проверяют оба
слоя отдельно, потому что мутация, ослабляющая только политику, через
функцию не видна.

**Статус «в сделке» вручную не ставится.** Он означает, что по подбору
создана сделка, и приходит из `create_deal_from_match()` (инвариант 2).
Иначе потребность показывала бы сделку, которой нет. Остальные статусы,
включая «закрыта» и «отвал», ставятся руками: клиент мог купить сам.

**Фильтры списков живут в URL, а не в состоянии компонента.** Ссылку на
отфильтрованный список можно отправить коллеге, а перезагрузка страницы не
сбрасывает подбор условий. Значения фильтров проверяются по белому списку
(`lib/list-params.ts`), поэтому подставить в запрос произвольное значение
через строку запроса нельзя.

**Активность приватна по умолчанию, но автор может поделиться.** Прежде
активности были видны только автору и админу — это было строже задания, и
обоснованно: заметка «звонил, +996…» обошла бы инвариант 4. Проверка
показала цену такой строгости: listing-агент видел **ноль** активностей
коллеги по своему объекту. Показ записан, а согласовать его нечем, и CRM
превращается в личный блокнот.

Поэтому у активности появился флаг `is_shared`. По умолчанию ложь. Аудитория
общей записи **узкая** — не «все агенты», а только тот, кто может
действовать по этой сущности: `can_edit_object` для объекта,
`can_lead_match` для подбора, `is_deal_party` для сделки, агент
потребности, owner_agent контакта. Свои записи видны всегда, чужие приватные
не видны никому кроме админа.

**Остаточный риск признаю.** Если автор напишет в общую заметку телефон
клиента и поделится ею на объекте, его прочтёт listing-агент объекта — а
инвариант 4 телефон клиента ему не даёт, пока нет активной сделки. Защита
здесь человеческая: приватно по умолчанию, узкая аудитория и прямое
предупреждение в форме ровно в момент, когда ставится галочка. Полностью
убрать риск можно только запретив делиться — и тогда согласовать показ в
системе будет нечем. Если в агентстве это неприемлемо, флаг убирается одной
правкой политики.

**`done` и `done_at` не расходятся.** Проверка нашла два принимавшихся
состояния: `done = true` без даты выполнения и дата выполнения в 2027 году
при `done = false`. Теперь дату ведёт триггер: отметили — зафиксировал,
сняли — стёр, будущую прижал к настоящему. Клиенту колонка `done_at` не
выдана вовсе.

**Свою строку агент видит при любом статусе** — политика
`agents_read_self` (`0013`). До неё `agents_read` требовала одобренного
агента, и неодобренный не видел даже себя. Следствие было не только про
чтение: Postgres применяет SELECT-политику при поиске строк для `UPDATE`,
поэтому `update agents set full_name = … where auth_user_id = auth.uid()`
у неодобренного задевал 0 строк — молча, без ошибки. Получался замкнутый
круг: админ видел заявку с почтой вместо имени, а человек не мог вписать
имя, пока его не одобрят.

Политики складываются по OR, поэтому это только расширение: одобренные
как и раньше видят всех, остальные — ровно себя. Заблокированному это тоже
нужно, иначе кабинет не может сказать, что доступ отозван, и показывает
общий экран ожидания. Форма имени доступна прямо на экране ожидания.

**Агент не может сам себя одобрить и повысить.** В `0006` политика
`agents_self_update` разрешала правку собственной строки, а грант был выдан
на таблицу целиком. Вместе это позволяло любому агенту выполнить
`update agents set status='approved', role='admin' where auth_user_id = auth.uid()`
и стать админом — проверено на схеме до `0011`, проходило. Закрыто двумя
независимыми способами: поколоночный грант (агенту выдано только
`full_name` и `phone`) и триггер `b_guard_agent_privileges`, который держит
правило даже если грант вернёт неосторожная миграция. Статус и роль меняются
только через `app.approve_agent()`, `app.block_agent()` и
`app.set_agent_role()`, и каждая проверяет админа сама.

Прямой доступ к базе правило обходит сознательно — условие
`auth.uid() is not null` в триггере. Иначе первого админа было бы не завести.

**Последнего админа нельзя заблокировать или разжаловать** —
`app.assert_admin_remains()`. Иначе систему можно запереть так, что одобрять
новых агентов станет некому.

**Функции кабинета лежат в `public`, а не в `app`.** PostgREST отдаёт `rpc`
только из открытых схем, поэтому `app.ensure_agent()` из кабинета был бы
недоступен. В `0012` добавлены пустые обёртки в `public`; схему `app` целиком
не открываем, чтобы наружу не смотрели `app.write_audit()`,
`app.can_see_contact()` и прочие внутренности. Проверяется тестом
`inv9_public_api` — ошибка, которую иначе поймал бы только живой прогон.

**Вход через Telegram не делается, якорь инварианта 6 — `auth_user_id`.**
Решено отдельно. Суть инварианта не изменилась: один человек — один аккаунт,
повторный вход не создаёт дубликат и не теряет владение объектами. Изменилось
то, чем он закреплён: вместо Telegram-идентичности это идентичность Supabase
Auth, и вход идёт через `app.ensure_agent()` — upsert по `auth.uid()`.
`telegram_id` стал необязательным, но остался уникальным: агентов без Telegram
может быть сколько угодно (NULL уникальности не нарушает), а два аккаунта на
один Telegram — по-прежнему нельзя.

Авторизацию это не задело вовсе: `app.current_agent_id()` и `app.is_admin()`
с самого начала опознают агента по `agents.auth_user_id = auth.uid()`, поэтому
инвариант 4, гейт «CRM только одобренным» и все политики RLS работают как
работали, с любым способом входа в Supabase Auth.

Вместе с этим появилось ограничение `agents_has_identity`: у агента обязана
быть хотя бы одна идентичность. Без него инвариант 6 получил бы дыру — строка
без `auth_user_id` и без `telegram_id` ни с каким входом не сопоставляется, но
владеть контактами и объектами может. Человек потом логинится, получает новую
строку, а объекты остаются за мёртвой. Это ровно та потеря владения, которую
инвариант 6 запрещает. Если вам нужно заводить агентов заранее, без всякой
идентичности, это ограничение придётся снимать осознанно.

**Перенос даёт мандат `active` + `contract_confirmed = false`**, а не
отдельный статус «требует подтверждения». Согласовано отдельно: иначе
инвариант 1 снял бы с публикации все переносимые объекты. Флаг уже есть в
модели мандата и означает ровно это.

**`app.expire_mandates()` вызывается по расписанию pg_cron** — миграция
`0009_schedule.sql`, ежедневно в 00:10 UTC (06:10 по Бишкеку, до начала
рабочего дня). Это единственное место, где инвариант 1 зависит от чего-то
вне базы, поэтому миграция устроена так:

- если `pg_cron` недоступен, она **не падает**, а выдаёт `WARNING`. Падение
  заблокировало бы всю цепочку миграций на свежем проекте Supabase, где
  расширение ещё не включено в панели;
- проверить, что расписание реально стоит, можно запросом
  `select * from app.schedule_health()`. Он показывает три вещи: установлен
  ли `pg_cron`, активно ли задание и нет ли уже просроченных активных
  мандатов — последнее и есть симптом неработающего расписания.

**После развёртывания запустить `app.schedule_health()` обязательно.** Молча
незапланированное истечение мандатов — худший из вариантов: инвариант 1
выглядит рабочим, а объекты висят в каталоге с просроченными договорами.

**Комиссия не выносится в публичную часть.** `public_catalog_v` не содержит
ни комиссии, ни агентов, ни внутреннего состояния; `deal_commission_v` и
`match_commission_v` у роли `anon` отозваны. Проверяется в приёмке.

## Слой доступа

Кабинет должен ходить через эти функции, а не UPDATE-ами по таблицам.
Инварианты держатся и при прямом UPDATE, но через функции клиенту физически
нечего передать неправильно: стороны комиссии и мандат выводятся на сервере.

| Функция | Назначение |
|---|---|
| `ensure_agent(name)` | вход; upsert по `auth.uid()` — основной путь (инвариант 6) |
| `approve_agent(id)` / `block_agent(id)` | одобрение и блокировка, только админ |
| `set_agent_role(id, role)` | смена роли, только админ |
| `update_my_profile(name, phone)` | правка своего имени и телефона |
| `transfer_contact(id, to_agent)` | клиент целиком: контакт, потребности, подборы |
| `transfer_object(id, to_agent)` | объект и listing-агент активного мандата |
| `app.can_see_entity_activity(type, id)` | кому видна общая активность по сущности |
| `find_contact_by_phone(phone)` | проверка перед созданием: не дубликат ли |
| `app.normalize_phone(phone)` | приведение номера к сопоставимому виду |
| `merge_contacts(keep_id, merge_id)` | склейка двух записей одного человека |
| `set_object_ownership(obj, contact, role, share)` | связь контакта с объектом |
| `set_agent_telegram(agent, telegram_id)` | привязка Telegram, только админ |
| `app.enqueue_due_reminders(horizon)` | что и кому напомнить; идемпотентна |
| `remove_object_ownership(obj, contact)` | снятие связи |
| `create_object(…)` | объект + собственник + мандат одной транзакцией |
| `update_object(…)` | правка объекта, право проверяется |
| `create_mandate(…)` / `terminate_mandate(…)` | договор с собственником |
| `create_requirement(…)` / `update_requirement(…)` | потребность клиента |
| `can_edit_object(id)` / `is_deal_party(id)` | права: страница спрашивает у базы |
| `create_deal_from_match(match_id)` | сделка; только сторона (инвариант 2) |
| `set_match_status(id, status, reason, showing_at)` | ведение подбора; `in_deal` не принимает |
| `can_lead_match(id)` | право вести подбор: страница спрашивает у базы |
| `set_deal_status(id, status)` | этап сделки; `closed` и `failed` не принимает |
| `close_deal(id, price)` / `fail_deal(id, reason)` | завершение; только сторона |
| `app.login_by_telegram(tg, name, auth_uid)` | вход, когда известен Telegram-id; upsert по `telegram_id` |
| `publish_object(id)` / `withdraw_object(id)` | публикация и снятие |
| `create_match(object_id, requirement_id)` | подбор; `closing_agent` = текущий агент |
| `create_deal_from_match(match_id)` | сделка; принимает ТОЛЬКО `match_id` |
| `close_deal(id, final_price)` / `fail_deal(id, reason)` | закрытие и срыв |
| `app.confirm_actual(object_id)` | подтверждение актуальности |
| `app.expire_mandates()` | истечение мандатов по дате, по расписанию |
| `app.backfill_missing_mandates()` | перенос: объекту без мандата — мандат |

## Что НЕ сделано

- **Вход и одобрение не проверены на живом Supabase.** Проверено: сборка,
  типы, что все вызываемые функции лежат в `public` и доступны роли
  `authenticated`, и что все запрашиваемые колонки существуют и отдаются под
  RLS. Но сам обмен письмами с Supabase Auth в этой сессии запустить было
  негде, поэтому настройку из раздела выше надо сделать и проверить руками.
- **Пароля нет, только ссылка на почту.** Сознательно: нет ни хранения
  пароля, ни восстановления, ни экранов смены. Если нужен пароль — это
  `signInWithPassword` плюс экран восстановления.
- **Публичного каталога как страниц нет** — только витрина
  `public_catalog_v`.
- **Загрузки фотографий нет** — только ссылки по одной в строке. Файлы это
  отдельная работа со Storage.
- **Объединение необратимо.** Присоединённая запись удаляется; её
  содержимое остаётся только в журнале действий, отдельной кнопки «вернуть»
  нет. Старые ссылки на удалённую карточку дают 404, а не перенаправление.
- **Дубликаты ищутся только по совпадению имени.** «Орозов Нурлан» и
  «Орозов Н.» в кандидаты не попадут — их придётся заметить глазами и
  склеить вручную через карточку.
- **Отправка напоминаний не проверена на живом Telegram** — токена не было,
  и посылать сообщения в реальный чат без спроса не следует. Всё до границы
  HTTP проверено тестами.
- **Напоминания только в Telegram.** Почта как канал не реализована: для неё
  нужен отдельный поставщик. Очередь к этому готова — у записи есть поле
  канала, добавить нужно только отправщика.
- **Агент не может привязать Telegram сам** — это делает админ.
  Самостоятельная привязка требует подтверждения через бота.
- **Активность нельзя назначить коллеге.** Запись всегда принадлежит тому,
  кто её создал; колонка `agent_id` клиенту не выдана именно поэтому. Задачу
  для другого агента поставить нечем.
- **Страницы не проверены на живой Supabase.** Проверено: сборка, типы и то,
  что все запрашиваемые колонки существуют и отдаются под RLS
  (`inv4c_page_queries`). Запустить страницы против настоящего PostgREST
  в этой сессии было негде.
- Выгрузка в lalafo и house.kg: таблица `publication_channels` описывает
  состояние, сами коннекторы не писались.
- Списки объектов и потребностей: есть только карточки по id.
- Ничего не задеплоено и не опубликовано.
