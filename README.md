# Платформа профессионалов — модель данных и серверные инварианты

Платформа аренды и продажи недвижимости в Бишкеке. Публичный каталог открыт
всем, CRM живёт внутри кабинета агента и открывается только агентам со
статусом «одобрен». Сайт и CRM — один продукт и одна база: **публикация
объекта это его состояние, а не выгрузка во вторую систему.**

## Где это работает

Боевой адрес: **https://liberterra.kg**

Всё на Cloudflare, Worker `partner`, аккаунт `Mirbekbekov@gmail.com's Account`:

| | |
|---|---|
| база | D1 `partner` — привязка `DB` |
| снимки объектов | R2 `partner-photos` — привязка `PHOTOS`, отдача через `/photos/*` |
| модель для черновиков описаний | Workers AI — привязка `AI` |
| письма со ссылкой для входа | Cloudflare Email Sending — привязка `EMAIL` |
| расписание | `triggers.scheduled` в `cloudflare.config.ts` |

**Ключей ни для чего из этого не существует.** Доступ выдаёт площадка
привязкой, а не строкой в секретах. Это и есть главная причина переезда
с Supabase: нечего хранить, нечего потерять и нечего случайно
опубликовать.

Секретами остались только три значения, которых привязкой не выдать:
`NEXT_PUBLIC_SITE_URL`, `CRON_SECRET` и `TELEGRAM_BOT_TOKEN`.

**На домене живут и чужие маршруты.** Они точнее, чем `/*`, поэтому
Cloudflare отдаёт эти пути им, а не нам. Трогать нельзя:

| Путь | Чей Worker | Зачем |
| --- | --- | --- |
| `/qr/*`, `/chayka*` | `qr-redirect` | напечатанные QR-коды |
| `/api/catalog-sync` | `hidden-pine-cbff` | выгрузка каталога старого сайта |
| `/requests.html` | `hidden-pine-cbff` | страница заявок старого сайта |

**Объявления старого сайта приезжают сами.** Старый сайт присылает свой
каталог на `/api/catalog-sync` чужому Worker'у, тот складывает его снимком
в базу `liberterra-catalog`. Наше расписание читает снимок привязкой
`CATALOG` (только чтение) и заводит из него ЧЕРНОВИКИ объектов —
`lib/db/catalog-import.ts`.

Черновики, а не публикации: без активного мандата публиковать нельзя, а
договоров в выгрузке нет. **Импорт только заводит и никогда не правит** —
один раз перенесённая карточка принадлежит агентству, и ночной прогон не
вправе затирать работу агента.

В выгрузке лежат не только объявления: на 27 ноября 2026 года из 283
строк 281 — это «Запрос», то есть человек ИЩЕТ жильё. Такие строки
пропускаются: объект из чужого поискового запроса не заводится. Что ещё
пропускается и почему — в `lib/catalog-csv.ts`.

**Пуш в ветку выкатывает сайт.** `.github/workflows/deploy-cloudflare.yml`:
зависимости, типы привязок, проверка типов, сборка, выкладка Worker и
применение схемы к базе. Нужны два секрета репозитория —
`CLOUDFLARE_API_TOKEN` (права Workers Scripts Edit, Workers AI Read,
D1 Edit, Workers R2 Storage Edit, Workers Routes Edit) и
`CLOUDFLARE_ACCOUNT_ID`.

**Как сайт себя называет, считается по каталогу.** В шапке и подвале место
подставляется: один город — он сам, несколько — страна. Иначе «Агентство
недвижимости, Бишкек» устарело бы ровно в тот день, когда кто-то заведёт
объект в Оше, и никто бы об этом не вспомнил. Пустой каталог остаётся
бишкекским: сайт без объектов всё равно бишкекский.

Заголовок страницы и описание для поиска при этом НАМЕРЕННО остались
бишкекскими. Их читает поисковик, а не посетитель, и «недвижимость в
Бишкеке» — запрос, который люди набирают; «в Кыргызстане» так не
набирают. Менять их значило бы потерять в поиске ради точности, которой
никто не увидит.

**Районы считаются по выбранному городу, схема — по тому, чья она.**
Раскладки живут в `lib/city-plans.ts`, по одной на город; `CityMap` не
знает ни одного города по имени и рисует то, что ему дали. Сейчас описан
один город — Бишкек.

Схема выводится, только когда ясно, какого она города, и такая схема есть:
городов несколько и ни один не выбран — схемы нет. Город без раскладки не
ломается, у него остаётся строка районов над каталогом: это названия, а не
география, и врать там нечему.

Схемы Оша нет сознательно, по решению владельца: пока объектов там нет,
она никому не видна, а рисовать её наугад нельзя. Появятся объекты — у
города будет строка районов без картинки: работает, просто беднее.

Город попадает в `city-plans.ts`, ТОЛЬКО когда раскладку назвал человек,
который этот город знает. Вся ценность схемы — в правде расположения:
местный должен узнать город с первого взгляда. Выдуманная раскладка хуже
отсутствия — отсутствие ничего не обещает, а неверная обещает и
обманывает. Названия в раскладке обязаны совпадать с тем, что агенты
пишут в поле зоны, иначе ячейка никогда не наберёт объектов.

**Фид для площадок.** `/feed.xml` — постоянный адрес со списком
опубликованных объектов в формате Яндекс.Недвижимости (YRL). Площадке
отдают ссылку, и дальше она читает сама: ни ключей, ни договорённостей о
протоколе, ни нашего кода на их стороне. Годится любой площадке, которая
умеет читать фиды, а не только lalafo и house.kg.

Строится ТОЛЬКО из витрины, и это не формальность: фид уходит наружу
целиком и навсегда, забрать из него поле нельзя. Витрина физически не
отдаёт ни агента, ни собственника, ни комиссии. Проверено прогоном —
отдельная проверка ищет в готовом файле имя агента, имя собственника и
телефон.

Контакт в объявлении — телефоны агентства из привязки `FEED_PHONE`
(`cloudflare.config.ts`), через запятую. Не агента: витрина телефонов не
отдаёт вовсе — там номера собственников. Номера приводятся к виду
`+996…`, повторы и мусор отбрасываются, а если не осталось ни одного
годного — блок контакта не выводится совсем. Пустой телефон площадка
приняла бы за настоящий, и по объявлению звонили бы в никуда.

Чего в нём нет и почему — в разделе «Что НЕ сделано»: коммерческих
объектов и настоящего города.

**Пересчёт миниатюр.** `/cabinet/admin/photos`, только админу. Находит в
хранилище снимки, у которых нет миниатюры, скачивает каждый, уменьшает его в
браузере и отправляет обратно. Нужен для снимков, загруженных до появления
сжатия, и для тех, чей браузер уменьшать не умеет.

Работу делает открытая страница, потому что уменьшить картинку в Worker'е
нечем. По одному, последовательно: узкое место — сеть, и десять
параллельных скачиваний ничего не ускорят. Нечитаемый файл пропускается, а
не обрывает остальное. Прерывать безопасно: каждая миниатюра сохраняется
сразу, а список строится из того, чего в хранилище нет, — повторный запуск
возьмёт только оставшиеся.

**Отказ в правах — это ответ, а не авария.** Агенту не-админу страница
печатает строку «Действие доступно только админу» в обычном оформлении, с
кодом 200; маршрут `/api/photos/thumbs` отвечает 403 с тем же текстом.
Ссылки в меню у не-админа нет вовсе.

Это стоит отдельного абзаца, потому что сперва было сделано неправильно, и
обнаружилось только на живом сайте. Исключение `Forbidden` улетало из
серверного компонента, и человек получал «This page couldn't load» с кодом
500. Ложь дважды: ничего не сломалось — ему просто нельзя; и выглядит это
как поломка сайта, а не как решение, принятое нарочно. Человек на таком
экране жмёт «Reload» и пишет, что сайт лёг.

Отсюда правило для любой страницы кабинета с проверкой прав: отказ
ПЕРЕХВАТЫВАЕТСЯ и показывается строкой — как на `/cabinet/admin/agents` и
`/cabinet/admin/photos`. Дать исключению улететь можно только там, где
ответ и должен быть аварией. Проверка типов этого не ловит: незаконченный
`try` компилируется прекрасно, а разница видна лишь в браузере.

**Выкатывает только `main`.** Рабочая ветка стояла в списке, пока работа не
была влита; 26 ноября 2026 она влилась, и строку убрали — иначе один и тот
же Worker выкатывался бы из двух мест, и по адресу сайта нельзя было бы
сказать, чей код там лежит. Значит пуш в рабочую ветку больше ничего не
выкатывает: чтобы изменения дошли до сайта, их надо влить в `main`.

**Прогон не появился — запустите вручную.** Он заводится примерно через
полминуты после пуша; смотреть здесь:
<https://github.com/mirbekbekov-glitch/Partner/actions>. Если через пару
минут прогона нет — кнопка «Run workflow» на странице выкладки, ветка
`main`.

Так однажды уже было: 25 ноября 2026 пуш `972776a` не завёл ничего, а
следующий, `7ddb767`, завёл обычным порядком. Дело не в настройке —
у пропавшего коммита нет набора проверок и от приложения `claude`, то
есть от второго, независимого приложения, которое к выкладке отношения
не имеет. Два разных приложения не могут промолчать из-за нашего файла:
потерялось само событие пуша, на стороне GitHub. Чинить тут нечего,
ручной запуск проходит с первого раза.

И не судите по первым секундам: сразу после пуша прогона в списке ещё
нет, и это не значит, что он не будет создан. Один такой поспешный вывод
уже стоил получаса разбирательства на пустом месте.

## Где живут проверки — и почему это главное

На Supabase таблицы торчали наружу через PostgREST, поэтому защита
**обязана** была жить в базе: RLS, триггеры, `SECURITY DEFINER`-функции.
Проверка в приложении защищала бы только приложение.

У D1 наружу не торчит ничего — дойти до неё может только Worker. Поэтому
инварианты переехали в `lib/db`, и обойти их нельзя не потому, что база
запрещает, а потому что **другого входа в базу нет**.

Цена этого размена названа прямо: RLS была страховкой от забытого условия,
и её больше нет. Забыть условие теперь можно. Поэтому:

- предикаты видимости записаны ОДИН раз в `lib/db/visibility.ts`, и
  двадцать запросов зовут три функции, а не повторяют условие двадцать раз;
- каждый предикат проверен мутацией: сломай его — и прогон краснеет с
  точным сообщением вроде «видно 11 контактов» или «посторонний чужих
  сделок не видит — видно 2»;
- состав публичной витрины задан одним списком колонок, и замена его на
  `o.*` роняет проверку, которая перечисляет запрещённые колонки поимённо.

## Запуск

```bash
npm install
npm run dev
```

Переменные — в `.env.example`. Для локальной работы нужен только
`NEXT_PUBLIC_SITE_URL`: база, хранилище, модель и почта приходят

## Прогон тестов

```bash
npm test
```

Это три вещи:

```
npm run typecheck    проверка типов — первой, до всего остального
npm run test:d1      277 проверок на настоящей D1
npm run test:forms   вложенных <form> нет
npm run test:public  публичная часть читает только витрину
```

Четвёртая проверка запускается руками и в `npm test` не входит:

```bash
npx esbuild lib/photo-resize.ts --bundle --format=esm --outfile=/tmp/resize.mjs
node tests/browser/resize.mjs /tmp/resize.mjs
```

Это сжатие снимков, и покрыть его основным прогоном нельзя в принципе:
сжимает браузер — `createImageBitmap`, `OffscreenCanvas`, кодировщик WebP, —
а в Worker'е ничего этого нет. Проверка поднимает настоящий Chromium,
рисует снимок 3000×2000 и смотрит, что вышло: 3,9 МБ → 794 КБ, полный
2000×1333, миниатюра 640×427. Картинка в ней — шум, то есть худший случай
для сжатия; настоящая фотография сжимается сильнее.

В выкладку не включено намеренно: браузер ставится полминуты, а
`lib/photo-resize.ts` меняется раз в полгода. Запускать при его правке.
Проверено мутациями, как и всё остальное: подними `FULL_SIDE`, смени WebP
на JPEG, сравняй `THUMB_SIDE` с полным — краснеет каждая.

**Проверка типов входит в `npm test` — и стоит первой.** Прогон на D1
собирается своим сборщиком, а не `tsc`, и однажды зелёные тесты уже
означали упавшую выкладку: в тестовом файле стояло `plan?.cells.some(...)`
вместо `boolean`, прогон этого не заметил, а шаг `typecheck` в выкладке
заметил. Это второй случай за день, когда «тесты зелёные» не означало
«выкладка пройдёт», поэтому проверка переехала в сам прогон.

**Правка `0001_schema.sql` НЕ доходит до существующей базы.** Таблицы там
создаются через `create table if not exists`, и на базе, где они уже есть,
весь файл — пустая операция. Поэтому новая колонка живёт в отдельной
миграции `000N_*.sql`, и всё, что от неё зависит — индексы в том числе, —
живёт в той же миграции, а не рядом с описанием таблицы.

Это стоило упавшей выкладки 26 ноября 2026: колонка `city` была и в 0001,
и в 0003, а индекс по ней — только в 0001. На боевой базе индекс выполнился
раньше `ALTER` и упал с «no such column: city». Worker к тому моменту уже
выложился, и фид отвечал 500, пока колонку не добавили вручную.

Прогон этого не ловит и поймать не может: он всегда поднимает базу с нуля,
где 0001 отрабатывает целиком. Путь «поверх существующей базы» проверяется
только самой выкладкой. Отсюда правило выше — его стоит соблюдать на
веру, а не надеяться на тесты.

**База в прогоне не поддельная.** Miniflare поднимает тот же движок, что
работает в продакшене, со всеми особенностями SQLite. Заглушены ровно три
вещи, которых вне Worker не существует: `cookies()`, модуль привязок и
отправка писем. Вход при этом НЕ обходится: тест кладёт строку в `sessions`
и cookie с токеном, то есть проходит тот же путь, что и браузер.

### Проверено мутациями, а не зелёным цветом

Смысл прогона не в том, что он зелёный, а в том, что он краснеет. Каждый
инвариант ломали и смотрели, что падает именно он:

| что сломали | что покраснело |
|---|---|
| публикация без проверки мандата | инв. 1: публикация без мандата |
| `published_at` переставляется заново | инв. 5: первая дата, дата при правке |
| снятый мандат не снимает объект | инв. 1: расторжение и истечение |
| обе доли комиссии округляются | инв. 3: `7501 + 7501 ≠ 15001` |
| удаление дубликата переставлено в начало | потребность исчезла БЕЗ ошибки: «у остающейся 0, всего 0» |
| closing-агент берётся по нажавшему | инв. 3: «вышло Анна» вместо Бориса |
| комиссия от цены объекта, не финальной | инв. 3: 800000 вместо 760000 |
| очередь перестала быть идемпотентной | второй проход уронил рассылку на UNIQUE |
| правка профиля принимает любые поля | «роль стала admin», «почта стала другой» |
| ссылка входа срабатывает повторно | вход: ссылка одноразовая |
| возврат после входа без проверки | «повела на `//evil.example.com/hack`» |
| в базу кладётся сам токен | «в базе лежит не сам токен, а его хэш» |
| предикат контактов открыт всем | 4 проверки, включая «видно 11 контактов» |
| сделки видны всем | «посторонний чужих сделок не видит — видно 2» |
| править можно любой объект | «счётчики считают только своё — объектов 9» |
| витрина отдаёт `o.*` | «просочилось: `created_by_agent_id`, `publication_state`» |

Две мутации не поймались с первого раза, и это нашло дыры **в тестах**:
проверка «правка профиля не трогает роль» смотрела только на честный
вызов, а проверка поиска не трогала правку адреса. Обе переписаны.

### Публичный каталог

Открытая часть — `/<язык>` и `/<язык>/objects/<id>`. Читает **только**
витрину `lib/db/catalog.ts`, в которой нет ни комиссии, ни агента, ни
собственника, ни контактов, и которая отдаёт лишь объекты в состоянии
`published`.

Это не вежливость страницы, а устройство. Состав выдачи задан ОДНИМ
списком колонок, и каждый запрос модуля собирается из него: дописать туда
«ведёт» можно только правкой этого списка, а это видно в рецензии и
ловится проверкой. Мутация, заменившая список на `o.*`, роняет её сразу —
«просочилось: `created_by_agent_id`, `publication_state`».

Рядом стоит проверка, что в самой таблице эти колонки ЕСТЬ. Иначе «в
выдаче нет агента» проходило бы и на пустом объекте, то есть ничего бы не
значило.

Правило «публичная часть читает только витрину» проверяется и структурно:
`tests/check-public.sh` не пускает публичный файл ни к `lib/db/sql`, ни к
кабинетным модулям.

Проверено на живых данных анонимом, без единой cookie: в исходнике страницы
нет ни имён агентов, ни собственника, ни телефонов, ни слова «комиссия»,
а черновой объект по прямой ссылке отдаёт 404, а не устаревшую цену.

Фильтры живут в строке запроса, поэтому ссылкой на подборку можно делиться
и её же видит робот поисковика. Каталог индексируется, кабинет и вход
закрыты `noindex` каждый сам за себя: общий запрет в корневом макете закрыл
бы заодно и каталог.

Поиск разбивается на слова, и каждое должно найтись в адресе или районе.
«чуй» находит «Чүй» — но не так, как кажется.

`lower()` в SQLite работает ТОЛЬКО с латиницей: «Чүй» он не меняет вовсе.
Поэтому полагаться на него в запросе нельзя, и у объекта есть отдельная
колонка `search_text` — нижний регистр, кыргызские буквы сведены к русским,
— которую заполняет код. Запрос проходит через ту же функцию перед
сравнением. Тот же приём, что у телефонов: нормализация в коде, а не в
запросе.

Колонка пересобирается при каждой правке адреса или района. Без этого
объект остаётся найденным по прежнему адресу и не находится по новому —
ошибка тихая, видна только человеку, который ищет и не находит.

Запятая в запросе — обычный разделитель слов: «Чүй, кв» это два слова. На
Postgres она однажды роняла весь запрос целиком, и человек видел пустой
каталог.

### Агентство недвижимости

Агент либо состоит в агентстве («Этажи» и подобные), либо работает сам.
Принадлежность он указывает при регистрации, на том же экране, где вписывает
имя.

Два правила, из которых следует остальное.

**Название уникально по нормализованному виду.** Иначе «Этажи», «этажи» и
«ЭТАЖИ» станут тремя агентствами, фильтр по источнику развалится, а сводить
их придётся руками. Тот же приём, что у телефонов контактов: ограничение,
которое обходится форматированием, хуже отсутствующего.

**Агент заявляет агентство, но не подтверждает его.** Иначе любой впишет
«Этажи» и прикроется чужой репутацией. Поэтому у связи есть отдельный
признак `org_confirmed`, и поднять его может только админ — правило держит
триггер, а не проверка внутри функции. Снять подтверждение может и сам
агент, сменив место работы: это не повышение прав. До подтверждения рядом с
названием в списке агентов стоит пометка «не подтверждено».

**Частный агент — это отсутствие организации**, а не агентство с названием
«Частный агент». Иначе такие агенты склеились бы в одно несуществующее
агентство.

### Чьи это объекты: источник в CRM

В списке объектов кабинета есть фильтр источника: мои, моего агентства,
других агентств или конкретный агент. Ответственным считается listing-агент
активного мандата, а у черновика без мандата — тот, кто его завёл: иначе
такие объекты выпадали бы из любого фильтра.

**В публичном каталоге этой возможности нет и не будет.** Каталогом
пользуются не только агенты, и внутреннее устройство агентства их не
касается: витрина (`lib/db/catalog.ts`) не содержит ни агентства, ни
собственника, ни комиссии. Это не договорённость, а проверка — состав
выдачи сверяется в «в витрине нет ни агента, ни комиссии, ни контактов»,
и попытка добавить туда колонку «ведёт» роняет прогон.

Исключение одно, и оно описано ниже: с 26 ноября 2026 витрина отдаёт имя
ведущего агента, его стаж и подтверждённый номер в реестре — три поля,
открытые сознательно и по отдельной проверке. Телефона и почты агента там
по-прежнему нет.

### Заявка с сайта

Под карточкой объекта — форма: имя, телефон, вопрос. Это **единственная
запись в базу от неизвестного**: до неё писать могли только одобренные
агенты. Поэтому поверхность сведена к одной функции `submit_lead()`, а
таблица заявок анониму не выдана вовсе — ни на чтение, ни на запись.

Проверки живут в базе, а не в форме: форму обойти тривиально, запрос уходит
прямо в PostgREST.

| | |
|---|---|
| объект | только опубликованный; на черновик и на несуществующий — один и тот же ответ, чтобы существование черновика не выяснялось перебором |
| имя | 1–120 символов |
| сообщение | до 2000 символов |
| телефон | нормализуется так же, как у контактов: `+996700112233` и `0700 11 22 33` — один номер |
| повтор | та же пара «телефон + объект» за сутки возвращает прежнюю заявку: человек нажал дважды, агент не должен звонить дважды |
| частота | не больше 5 заявок с номера в час и 30 на объект в час |
| бот | в форме скрытое поле-приманка; заполнено — ответ как при успехе, но в базу ничего не идёт |

Телефон заявителя — такой же чувствительный, как телефон собственника, и
живёт по тому же правилу: видит тот, кто ведёт объект, и админ. Предикат
взят тот же, что у правки объекта, — иначе вышло бы, что снять объект с
публикации агент не может, а читать телефоны его заявителей может.

По заявке заводится задача тому, кто ведёт объект, со сроком через два часа
— и дальше её подхватывают обычные напоминания. Заявка, о которой никому не
сказали, бесполезна.

Заявки в кабинете — `/cabinet/leads`: взять в работу, отработана, спам.

Оформление публичной части перенесено из прототипа: поиск отдельной
панелью в герое, сетка карточек, сортировка ссылками, карточка объекта с
прилипающей формой заявки. Шрифт — Manrope из дизайн-системы, поверхности
тёплые нейтральные (`surface-100/200/raised`), шкала отступов 4px.

Фотографии объектов есть не всегда: агент заводит объект с телефона, снимки
добавляет позже. Вместо серого прямоугольника рисуется фасад
(`app/Facade.tsx`), и строится он **из данных самого объекта**: этажность
задаёт высоту, комнаты — число окон, площадь — ширину. Поэтому дома в
каталоге отличаются друг от друга тем же, чем отличаются объекты. Тот же
рисунок подставляется, когда ссылка на фото протухла.

Метки на карточке только те, за которыми есть данные. «Подтверждён сегодня»
считается из `actual_at`, то есть из инварианта 5. Метки «Топ» нет: ей
неоткуда взяться, кроме как из выдумки.

Фирменный цвет — красный `#BE2C28`, взят пипеткой из знака, а не на глаз.
На белом он даёт 5.87 : 1 и годится для обычного текста; на тёмной теме —
только 3.09 : 1, поэтому там свой оттенок того же тона, `#DA524E` (4.57 : 1),
и текст на кнопках становится тёмным: белый на светло-красном дал бы 2.6 : 1.

Из-за этого пришлось развести ошибку и фирменный цвет: раньше ошибка была
красной надписью, а теперь красный — цвет ссылок и кнопок, и одним тоном их
не различить. Ошибка отличается **формой**: плашка с подложкой и полосой
слева, текст темнее фирменного. Все пары проверены по контрасту в браузере,
в обеих темах.

Название агентства — Liberterra. В шапке стоит знак (`public/liberterra.png`),
подписи рядом нет: в самом знаке уже написано «Liberterra», а имя, набранное
дважды, читается как ошибка вёрстки. Название остаётся в `alt` — для тех, кто
слушает страницу, и на случай, если картинка не загрузилась. Иконка вкладки
(`app/icon.png`) вырезана из квадратной части знака.
Заголовок каталога держится отдельно от бренда (`CATALOG_TITLE`): в шапке
стоит имя, а заголовок страницы должен говорить, что на ней лежит.

Телефоны агентства стоят в шапке на каждой публичной странице, все три
сразу: это разные операторы, и человек выбирает тот, что дешевле ему. Живут
в `lib/agency.ts` — одно место на весь сайт. На узком экране номера уходят
на свою строку целиком, а не прячутся за «показать номер»: спрятанный
телефон — это потерянный звонок.

### Вход

Вход по ссылке на почту, свой. Пароля нет сознательно: его забывают,
повторяют с других сайтов и восстанавливают через ту же почту — то есть
почта всё равно остаётся ключом, только с лишним звеном.

Как устроено: человек вводит почту → в базу кладётся ХЭШ одноразового
токена, сам токен уходит письмом → переход по ссылке обменивает токен на
сессию. Токен существует ровно в одном месте — в письме; в базе лежит
только SHA-256, поэтому утечка таблицы входа не даёт войти.

Токен гасится ТЕМ ЖЕ запросом, который его проверяет: `update … where
used_at is null`, и ноль изменённых строк означает «ссылку уже
использовали». Проверить, а потом отметить двумя действиями нельзя — два
одновременных перехода по одной ссылке дали бы две сессии.

Ответы намеренно неразличимы там, где разница что-то выдаёт:

- истёкшая, использованная и несуществующая ссылка отвечают одинаково —
  иначе чужие ссылки перебираются;
- запрос входа отвечает одинаково для известной и неизвестной почты —
  иначе форма входа становится проверкой «есть ли такой агент», а список
  сотрудников агентства не публичные данные.

Возврат после входа ограничен своими путями. Без этого ссылка из письма
становится открытым перенаправлением: «войдите» ведёт на чужой сайт,
похожий на наш.

Выход снимает ровно одну сессию, ту, из которой вышли. Выходить на одном
устройстве и терять вход на остальных человек не ожидает.

**Письма идут через Cloudflare Email Sending**, домен `liberterra.kg`.
Ключа нет — отправка идёт привязкой `EMAIL`.

На бесплатном плане Workers отправка возможна только на ПОДТВЕРЖДЁННЫЕ
адреса получателей. Для входа агентов это ограничение существенное: адрес
нового агента заранее никто не подтверждал. Снимается платным планом
Workers.

#### Приглашение ссылкой: обход ограничения на письма

Из ограничения выше следовало, что **завести второго агента было нельзя
вовсе**. Форма входа отвечает одинаково всем — «письмо отправлено», так
решено нарочно, — и новый человек просто ждал письма, которого не будет.
Снаружи это выглядит поломкой сайта, а не ограничением плана.

Поэтому ссылку выдаёт админ: `/cabinet/admin/agents`, форма «Завести
агента». Агентство и так заводит людей через WhatsApp, и ссылка идёт тем
же путём. Почта остаётся ключом учётной записи — меняется только способ
доставки первой ссылки.

Отдельной таблицы у приглашений нет намеренно: это тот же токен входа, в
`login_tokens`, и гасит его ТОТ ЖЕ запрос. Две таблицы означали бы две
проверки одноразовости, и вторая однажды отстала бы от первой. Отличает
приглашение колонка `issued_by_agent_id`: у обычного входа там пусто, у
приглашения — админ.

**Срок суточный, а не пятнадцать минут.** У обычного входа человек сам
нажал «войти» и смотрит в ящик. Здесь ссылку надо переслать, а получатель
может спать. Пятнадцать минут означали бы, что половина приглашений
протухает в переписке и админ выдаёт их по второму разу — ссылок стало бы
больше, а не меньше.

**Учётная запись заводится сразу, а не при первом входе.** Админ видит
приглашённого в списке и одобряет заранее. Иначе человек проходит по
ссылке, попадает на экран «ждите одобрения», и админ узнаёт об этом из
его звонка.

**Заблокированному ссылка не выдаётся** — отказ здесь, а не на входе.
Вход ему всё равно откажет, но тогда админ отправит ссылку, человек по
ней придёт и увидит «доступ закрыт», решив, что его отключили только что.
Разблокировка — отдельное осознанное действие.

**Приглашения не идут в часовой предел входа.** Предел в пять запросов
стоит против того, кто жмёт «войти» снаружи без спроса. Считай и выдачи
админа — пять приглашений подряд закрывали бы агенту вход на час, то есть
предел бил бы по тому, кого защищает. Проверено мутацией: убери
`issued_by_agent_id is null` из счётчика — падает «после шести
приглашений агент всё равно войдёт сам».

**Чего это не решает.** Повторный вход. Сессия живёт тридцать дней; когда
она истечёт, агент запросит ссылку сам — и письмо снова не дойдёт.
Значит ссылку придётся выдать заново, и так до платного плана. Повторная
выдача этим же экраном и делается: форма видит, что человек уже
заведён, и говорит об этом («уже был в списке — выдана новая ссылка»),
а имя существующего агента пустым полем не затирается.

**Честно о риске.** Ссылку держит в руках админ, значит выдавший может
войти вместо приглашённого. Это цена обхода, и прятать её незачем:
поэтому выдача пишется в журнал с именем выдавшего (`agent_invite`), срок
у неё сутки, а в самом экране сказано прямо — «кто по ней пройдёт, тот и
войдёт как этот агент, передавайте лично, а не в общий чат».

### `lower()` в SQLite и кириллица: разбор всех мест

Подвох один и тот же, и он стоил трёх ошибок, из которых две нашлись не
сразу. `lower()` в SQLite приводит ТОЛЬКО латиницу. Проверено запросом к
боевой базе, а не по памяти:

| выражение | результат |
|---|---|
| `lower('ОРОЗОВ Нурлан')` | `ОРОЗОВ Нурлан` |
| `lower('OROZOV Nurlan')` | `orozov nurlan` |

Для адресов объектов это было учтено сразу — колонка `search_text` и
функция `searchText()`, которая заодно сводит кыргызские буквы к русским.
А вот три других места его не учитывали:

| Где | Что было сломано |
|---|---|
| поиск контакта по имени | «орозов» не находил «Орозов» |
| поиск по тексту потребности | «тёплый» не находил «ТЁПЛЫЙ» |
| поиск дубликатов контактов | один человек, записанный капсом, дубликатом не считался |

Первые два исправлены колонками `search_text` у `contacts` и
`requirements` (миграция `0007`), заполняет их код той же функцией, что и
у объектов. Третий — правилом в коде, см. раздел ниже: там сравнение на
SQL не выражается в принципе.

**Почему колонкой, а не сравнением в коде.** Отбор идёт вместе с
постраничной выдачей и `count(*) over ()`. Сравнение в коде отфильтровало
бы только загруженную страницу, и счётчик врал бы.

**Колонку надо обновлять вместе с полем.** Проверено мутациями: убери
`next.search_text` из правки имени — падает «переименованный контакт
находится по новому имени»; то же для текста потребности.

**Заодно нашлась четвёртая ошибка, другого рода.** Поиск контактов искал
ещё и по телефону: `cp.phone_normalized like ?3`, где шаблон —
`%` + цифры запроса + `%`. При текстовом запросе цифр нет, шаблон
превращается в `%%`, и он совпадает с ЛЮБЫМ номером: поиск по имени
отдавал всех, у кого есть телефон. Условие по телефону теперь
добавляется только когда в запросе есть цифры. Проверено мутацией:
верни безусловное условие — падает «и по прежнему имени больше нет».

#### То же самое ломало ПОРЯДОК списков

Побайтное сравнение бьёт не только по поиску. SQLite сортирует строки по
кодам символов, и для кириллицы это значит, что все заглавные идут перед
всеми строчными. Проверено запросом к боевой базе:

```
order by name  →  Абрамов | Орозов | Яковлев | абрамов | яковлев
```

То есть контакт, записанный строчными, уезжал в конец списка — после
«Яковлева». `collate nocase` не помогает: он тоже знает только латиницу.

Сортировка по имени контакта и по адресу объекта (в списке объектов и в
списке сделок) переведена на `search_text`. Маленькие непостраничные
списки — коллеги и агентства — сортируются в коде через
`localeCompare(…, 'ru')`; в постраничных так нельзя, там порядок обязан
быть в запросе, иначе переставлялась бы только загруженная страница.

**Выбор пары для проверки здесь важнее самой проверки.** Первая версия
теста сравнивала «Абрамов» и «яблоков» — и проходила на сломанной
сортировке: «А» это U+0410, «я» — U+044F, то есть побайтный порядок на
этой паре СОВПАДАЕТ с алфавитным. Поймано мутацией. Годится только пара,
где порядки расходятся: строчная ранняя буква против заглавной поздней —
«абрамов» (U+0430) и «Яковлев» (U+042F).

Та же ошибка повторилась в проверке порядка по имени агента, уже после
того как была описана здесь: пара «Абаев»/«ядрин» снова совпадала в
обоих порядках, и мутация прошла молча. Правило короткое: **в проверке
порядка строчная буква обязана быть РАНЬШЕ по алфавиту, чем заглавная.**
И проверка обязана требовать, чтобы оба имени были в выдаче: без этого
она проходит на пустом списке — так и случилось, когда переименованные
агенты не вели ни одной записи из проверяемого списка.

**Имя агента — колонкой `name_sort`** (миграция `0008`). Решение
принято, а не отложено: у объектов, контактов и потребностей такая
колонка уже есть, и четвёртая по тому же образцу — это
последовательность, а не выбор между продуктовыми вариантами. Списки
постраничные, поэтому порядок обязан стоять в запросе.

Цена названа прямо: имя агента пишется в ТРЁХ местах — заведение,
переименование при входе, правка профиля, — и колонку надо обновлять в
каждом. Именно этот риск был доводом ПРОТИВ колонки у поиска
дубликатов; здесь он закрыт тремя проверками, по одной на путь, и каждая
падает, если своё место забыли. Проверено мутациями.

**Чего не исправлено.** Сортировка по полю «источник» у контакта
по-прежнему побайтная: отдельной колонки под него нет, а само поле —
свободный текст, который почти не сортируют. Если понадобится — тот же
приём.

**Старые строки.** Колонки `search_text` и `name_sort` появились со
значением по умолчанию — пустой строкой. Заполняет их код при записи, так
что строки, созданные ДО выкладки, не искались бы и сортировались бы
первыми.

Для контактов, потребностей и объектов переносить было нечего: на момент
выкладки их в боевой базе было по нулю — проверено запросом. **А вот
агентов я не проверил, и там строка была.** У неё `name_sort` остался
пустым, то есть имя сортировалось бы первым в любом списке. С одним
агентом это незаметно, со вторым — уже неверный порядок.

Починка сделана в коде, а не правкой боевой базы: `ensureAgentByEmail`
при входе видит пустую колонку и заполняет её по имени, которое уже стоит
в строке. Это не изменение данных, поэтому записи в журнал нет. Так
чинятся все такие строки сами, без отдельного переноса. Проверено
мутацией: убери починку — падает «пустое сопоставимое имя починилось при
входе».

Урок общий: добавляя колонку со значением по умолчанию, проверять надо
КАЖДУЮ таблицу, которую она затронула, а не те, про которые помнишь.

### Выгрузка списков в CSV: файл не должен исполняться

Выгрузка появилась вместе со списками, а описана не была; проверок на неё
тоже не было. Решения в `lib/csv.ts` неочевидные, и каждое теперь закрыто
проверкой — защита без проверки однажды тихо исчезнет при правке.

**Значение, начинающееся с `=`, `+`, `-` или `@`, Excel и LibreOffice
считают формулой.** Заметка агента `=HYPERLINK("…","Нажмите")` стала бы в
файле ссылкой, по которой кто-то щёлкнет; `=1+1` превратилось бы в
двойку. Перед такими значениями ставится апостроф: в ячейке он не виден и
делает её текстом. В базе при этом ничего не меняется — это защита файла,
а не данных. Табуляция и возврат каретки в начале значения закрыты по той
же причине: ими формулу тоже можно начать.

Проверено мутациями: убери защиту — падают все шесть проверок на опасные
значения; сузь её до одного `=` — падают четыре из шести.

**Разделитель — точка с запятой, в начале файла метка порядка байтов.**
Excel в русской локали читает запятую как десятичный знак и кладёт всё в
одну колонку; без метки принимает UTF-8 за однобайтовую кодировку, и
кириллица превращается в кракозябры. Оба решения — ради того, чтобы файл
открылся двойным щелчком, а не через мастер импорта. Переводы строк —
CRLF, как требует RFC 4180 и как ждёт Excel.

**Видимость выгрузка не ослабляет.** Она зовёт ту же функцию, что рисует
страницу, поэтому инвариант 4 отсекает чужое в самом запросе. Проверено
мутацией с другой стороны: сделай предикат видимости всегда истинным —
падает «а чужого в выгрузке нет» вместе с пятью проверками списков.
Выгрузка — другой способ посмотреть, а не способ обойти.

**Без входа выгрузка отвечает 403, а не пятисотой.** Отказ слоя доступа
отдаётся как отказ: человек без сессии должен получить внятный ответ, а
не «что-то сломалось».

### Объединение контактов: что остаётся в журнале

Объединение — единственное действие в системе, которое **удаляет** данные
насовсем. Присоединённая запись исчезает, отмены нет. Значит журнал — не
подстраховка, а единственное место, где её содержимое вообще остаётся.

**До 27 ноября 2026 там лежало одно имя.** README при этом обещал
«содержимое»; обещание было неверным, и заметно это стало бы только в тот
день, когда кто-то попросит вернуть запись. Теперь в журнал пишется всё,
из чего её можно собрать руками: вид, telegram, источник, роли, заметка,
владелец, дата появления и куда её влили.

**Телефонов там нет, и это не пропуск.** Они не удаляются, а переезжают к
остающейся записи. Общее правило журнала — не складывать в него телефоны
при каждой правке соседнего поля — остаётся в силе.

**Снятые связи собственности выписываются ДО удаления.** Роль входит в
ключ связи: если обе записи указаны собственниками одного объекта в одной
роли, лишняя снимается навсегда. Это единственное, что объединение
по-настоящему теряет, и раньше в отчёте оставалось только число «снято:
1». Теперь в журнале лежит, ЧТО именно снято — объект, роль и доля.
Проверено мутацией: выписывай после удаления — падает «и снятая связь
собственности выписана целиком».

### Поиск дубликатов: почему правило в коде, а не в запросе

Сравнение имён живёт в `lib/contact-match.ts`, а запрос лишь подтягивает
данные найденных. Две причины, и первая — исправленная ошибка, а не
удобство.

**`lower()` в SQLite не трогает кириллицу.** Проверено запросом к боевой
базе: `lower('ОРОЗОВ Нурлан')` возвращает строку без изменений, тогда как
`lower('OROZOV Nurlan')` даёт `orozov nurlan`. Прежний поиск сравнивал
`lower(trim(a.name)) = lower(trim(b.name))`, то есть для русских имён
сравнивал **с учётом регистра**: один и тот же человек, записанный капсом,
дубликатом не считался. Это была неверная проверка, а не ограничение.
`toLowerCase()` в JS кириллицу приводит.

**«Орозов Н.» на SQL не выразить.** Правило такое: совпадает первое слово
(фамилия), и каждое следующее слово одного является началом
соответствующего слова другого. «Орозов Нурлан» и «Орозов Н.» — одно
лицо; «Орозов Нурлан» и «Орозов Азамат» — разные.

**Одно слово против нескольких — НЕ совпадение.** «Орозов» и «Орозов
Нурлан» объединять нельзя: однофамильцев больше, чем тёзок, а объединение
необратимо — присоединённая запись удаляется. Лучше не предложить
дубликат, чем склеить двух разных людей. Проверено мутацией: убери
проверку длины — падает «„Орозов“ и „Орозов Нурлан“ — разные».

**Хранимой нормализованной колонки нет** — в отличие от телефонов, где
есть `phone_normalized`. Она закрыла бы только регистр, зато её пришлось
бы поддерживать при заведении, правке и объединении, и однажды одно из
трёх отстало бы. Правило инициалов она не закрывает вовсе, так что запрос
всё равно не стал бы одним сравнением.

**Цена: имена своих контактов читаются целиком**, с явным пределом
`DUPLICATE_SCAN_LIMIT = 1000`. Предел назван прямо, а не подразумевается:
молчаливое усечение означало бы, что дубликат иногда не находится и никто
не знает почему.

**Владелец проверяется дважды** — и в выборке имён, и в запросе за
телефонами. Снятие одной из двух проверок прогон не валит, и это
проверено мутацией; дубль оставлен намеренно, потому что каждая из них
стоит на пути к чужому телефону, а одна проверка была бы ровно одной
опечаткой до утечки.

### Задачу можно поставить коллеге и передать коллеге

Агентство так и работает: «посмотри объект вместо меня». До сих пор запись
принадлежала тому, кто её создал, и передать её было нечем.

**Ставить и передавать можно задачу и показ, но не заметку и не звонок.**
Заметка — запись о том, что сделал ТЫ; приписать её другому значило бы
сочинять за него историю. Поэтому выбор «на кого» показывается только для
задачи и показа.

**Передаёт тот, на ком запись, или админ** — то же правило, что у закрытия
и удаления. Иначе задачу можно спихнуть любому: пришёл, нашёл чужую
строку, переписал владельца.

**Только одобренному.** Неодобренный в кабинет не войдёт, заблокированный
потерял доступ — задача на любого из них это задача, которую никто не
увидит, и искать потом будут не её, а причину, по которой её не сделали.

**Напоминание едет за задачей, и это главное здесь.** Очередь хранит
агента ОТДЕЛЬНОЙ колонкой (`notifications.agent_id`), а не берёт его из
задачи при отправке. Значит без переписывания очереди «позвоните клиенту»
ушло бы ПРЕЖНЕМУ владельцу по задаче, которой у него больше нет, а новый
не получил бы ничего. Перенос идёт тем же батчем, что и смена владельца.
Проверено мутацией: убери перенос — падает «и напоминание уехало за ней».

**Уже отправленное напоминание не переписывается.** Его агент — факт о
прошлом, и правка была бы подделкой истории. Переносятся только `pending`
и `sending`. Проверено мутацией: сними фильтр по статусу — падает
«отправленное напоминание осталось на прежнем агенте».

**Значение `agent_id` проверяется в слое доступа, а не в форме.** До
появления выбора в форме этот параметр существовал в `createActivity`, но
был недоступен из браузера, и непроверенным быть не мог. Как только он
стал доступен, непроверенное значение означало бы задачу на кого угодно —
включая того, кого выставили за дверь. Внешний ключ поймал бы выдуманный
идентификатор, но ответом был бы `D1_ERROR: FOREIGN KEY constraint
failed`, а не внятный отказ.

**Список коллег отдаёт только имя и идентификатор.** Его видит любой
агент, а телефоны и почты коллег в выпадающем списке не нужны никому,
зато утекают вместе с ним. Проверено мутацией: допиши `a.email` — падает
«и только имя, без почты и телефона».

### Напоминания о задачах

Рассылку запускает расписание Worker — `triggers.scheduled` в
`cloudflare.config.ts`. Платформа вызывает не URL, а функцию `scheduled()`
в `worker/index.ts`, и та отдаёт запрос тому же обработчику, что
обслуживает посетителей: второй копии логики рассылки нет.

**Раз в сутки, в 9:07** — наследство Vercel: там бесплатный тариф разрешал
один запуск в день. Cloudflare так не ограничивает, и ежечасное расписание
ничего не стоит: достаточно написать `'7 * * * *'` в `cloudflare.config.ts`.
Код рассылки идемпотентен и рассчитан на любую частоту.

Пока расписание суточное, помните о следствии: напоминание о задаче придёт
в ближайший запуск, то есть в худшем случае почти через сутки.

Этим же расписанием делаются ещё две вещи: гашение истёкших мандатов
(инвариант 1 держится датой, а дата сама себя не проверяет) и уборка
протухших сессий и ссылок входа. Одно расписание на всё — все три задачи
идемпотентны и дёшевы, а отдельное пришлось бы заводить и помнить.

Нужны два секрета: `CRON_SECRET` и `TELEGRAM_BOT_TOKEN` — см.
`.env.example`.

**Проверено на живом Telegram целиком, 27 ноября 2026.** Сначала привязка:
кнопка в кабинете, ссылка, бот, секретный заголовок, гашение кода, запись
идентификатора, ответ человеку. Затем доставка: задача со сроком двухчасовой
давности, запуск `/api/cron/reminders`, и через 1,6 секунды сообщение в
чате. Запись в `notifications` — `kind: overdue`, `channel: telegram`,
`status: sent`, одна попытка, без ошибки.

Текст собрался по состоянию, а не по шаблону: рассылка увидела истёкший
срок и выбрала «Просрочено» вместо «Скоро срок», подтянув имя контакта, к
которому привязана задача.

Прогоном при этом по-прежнему проверено то, что живой проверкой не
покажешь: идемпотентность, отмена при выполнении, защита от двойной
отправки, отчёт о неудаче.

Агент без привязанного Telegram получает запись со статусом
«нечем доставить», а не тишину: в списке задач это видно, и профиль
объясняет, что делать.

**Агент привязывает Telegram сам.** В профиле он нажимает «Привязать
Telegram», получает ссылку `t.me/<бот>?start=<код>` и открывает её; бот
получает от Telegram НАСТОЯЩИЙ идентификатор отправителя и привязывает
его. Подделать нельзя: идентификатор приходит от Telegram, а не от
человека. Раньше это делал админ по присланному номеру — и верил человеку
на слово, проверить номер было нечем.

Код одноразовый, живёт 10 минут и хранится отпечатком: в базе только
SHA-256, сам код существует ровно в одной ссылке — то же устройство, что
у входа по почте. Ссылка показывается, а не открывается сама: кабинет
держат на компьютере, а Telegram стоит на телефоне. Отвязать агент может
сам, иначе единственным выходом снова был бы админ.

Привязка разрешена и ожидающему одобрения: напоминания нужны с первого
дня работы, а одобрения можно ждать сутки. Заблокированному закрыто всё.

**Обработчик бота отключён без секрета.** `/api/telegram/webhook` открыт в
интернет и входа не спрашивает — спрашивать нечего, запрос приходит от
Telegram. Кто угодно мог бы прислать `/start <чужой код>` со своим
идентификатором и забрать чужие напоминания. Останавливает это только
секретный заголовок, который Telegram получает при установке обработчика.
Не задан `TELEGRAM_WEBHOOK_SECRET` — маршрут отвечает 503 и тела не
читает: открытый обработчик хуже неработающей привязки, неработающую видно
сразу.

`TELEGRAM_WEBHOOK_SECRET` намеренно НЕ объявлен в `cloudflare.config.ts`.
Объявленный секрет — это требование при выкладке: пока он не задан на
Worker, выкладка отказывается, и 26 ноября 2026 она так и отказалась,
остановив выкладку всего сайта из-за одного маршрута. Защита при этом не
теряется: маршрут без секрета отвечает 503, то есть незаданный секрет
привязку выключает, а не открывает. Цена названа честно — о незаданном
секрете узнаёшь не при выкладке, а когда привязка не работает.

Чтобы привязка заработала, нужны три шага руками:

```bash
npx cf secret put TELEGRAM_BOT_TOKEN
npx cf secret put TELEGRAM_WEBHOOK_SECRET
```

```bash
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -H 'content-type: application/json' \
  -d '{"url":"https://liberterra.kg/api/telegram/webhook","secret_token":"<ТОТ ЖЕ СЕКРЕТ>"}'
```

И вписать имя бота в `TELEGRAM_BOT_USERNAME` в `cloudflare.config.ts` —
оно не секрет, его и так видно в чате. Пока имя пустое, кабинет честно
говорит, что бот не настроен, вместо ссылки в никуда.

### Карточка агента: лицо, стаж, сертификат

Объявление ведёт человек, и покупатель решает не только по квартире, но и
по тому, с кем ему разговаривать. До сих пор про агента не было известно
ничего, кроме имени.

**Стаж хранится ГОДОМ НАЧАЛА, а не числом лет.** «5 лет», записанное
сегодня, через два года станет неправдой, и поправить это никто не
вспомнит. Год не протухает: число лет считается при показе, вместе с
правильным окончанием — «год», «года», «лет».

**Сертификат заявляет агент, подтверждает админ** — тот же порядок, что у
агентства. Номер видит клиент, а непроверенное утверждение от имени
агентства остаётся обманом, даже если агент не хотел обмануть. Разница с
агентством в цене ошибки: принадлежность к фирме клиент хотя бы может
проверить звонком, квалификацию — нет.

**Смена номера сбрасывает подтверждение.** Без этого порядок обходится в
два приёма: вписать настоящий номер, дождаться отметки админа, затем
подменить его на любой другой и остаться с галочкой. Проверено мутацией:
убери сброс — падает «смена номера сбрасывает подтверждение».
Подтверждать пустое поле тоже нельзя, иначе отметка повиснет на пустоте, а
номер впишут после.

**Аватарка лежит по детерминированному ключу** `avatars/<id агента>.<расш>`:
новая затирает старую, а не копится рядом. Прежнее лицо агента никому не
нужно, а мусор в хранилище нужен ещё меньше. Если формат сменился, старый
файл убирается явно — иначе он остался бы лежать и отдаваться по своему
адресу. Ключ пишется в карточку агента тем же действием, что и файл в
хранилище: иначе страница и хранилище разойдутся.

Кеш у аватарки короткий, пять минут, в отличие от снимков объектов. Там
ключ случайный и содержимое по нему неизменно — можно кешировать вечно.
Здесь ключ постоянный, а содержимое меняется, и вечный кеш солгал бы.

**Клиенту открыты ровно три поля** — имя, стаж и подтверждённый номер в
реестре. Витрина (`catalogAgent`) выбирает их по именам столбцов, а не
`select ag.*`: при `*` любой новый столбец в `agents` уехал бы на публичную
страницу молча, в тот же день, когда его добавили. Телефона и почты агента
там нет намеренно — звонок идёт в отдел продаж, иначе объект уводят мимо
агентства. Проверено мутацией: допиши в выборку `ag.phone` — падает «в
выдаче агента нет ни телефона, ни почты, ни идентификатора», и в
сообщении видно, что именно просочилось.

Неподтверждённый номер витрина не отдаёт вовсе: `case when
certificate_confirmed = 1 then certificate_no end`. Не «отдаёт с пометкой
„не проверено“» — пометку клиент не читает, а номер выглядит документом.

Стаж считается от года, а не хранится числом лет: «5 лет», записанное
однажды, через два года станет неправдой, и поправить это никто не
вспомнит.

Блок показывается только у опубликованного объекта с активным мандатом —
то есть у того, кого витрина и так отдаёт. Проверено мутацией: убери
`publication_state = 'published'` — падает «но агента витрина по нему не
отдаёт»; у объекта в этой проверке мандат есть, иначе проверка была бы
пустой и мутацию не поймала бы.

Вместо незагрузившейся аватарки — две буквы имени. Пустой кружок читается
как «фото не загрузилось», две буквы — как сознательный выбор.

### Первый админ

Пока админа нет, одобрять агентов некому. Первого заводят прямым доступом
к базе, мимо слоя доступа — это единственный законный обход, и он возможен
только у того, у кого есть доступ к Cloudflare:

```bash
npx cf d1 query <id базы> --sql "update agents set role = 'admin', status = 'approved' where email = 'you@example.kg'"
```

Система не может назначить первого админа сама, и это не недоработка:
агент не вправе повысить себя, иначе правило «одобряет админ» не стоит
ничего.

Все семь на месте. Изменилось, ЧЕМ они держатся: часть по-прежнему схемой,
часть — кодом, через который проходит единственный путь к базе.

## Разбор слоя доступа на обход

`docs/ACCESS-AUDIT.md` — запись сквозной проверки: метод, 14 проверенных
путей, пять найденных дыр и чем они закрыты. Два факта, из которых там всё
следует, стоит держать в голове при любой правке:

1. **`SECURITY DEFINER` обходит RLS.** Проверка прав обязана быть внутри
   функции; политика её не подстрахует.
2. **Политика ограничивает строки, а не колонки.** `grant update on t` плюс
   политика «правь свои строки» означает «правь любую колонку своих строк».
   Правило про колонку держит поколоночный грант или триггер.

## Решения, которые стоит знать

**Почти всё ниже было решено на Postgres.** Факты, измерения и причины
остались верными — они про предметную область, а не про базу. Изменилось
одно: там, где написано «держит политика RLS» или «обходит прямой запрос к
PostgREST», теперь держит код `lib/db`, а прямого запроса к базе не
существует вовсе. Где это меняет суть, сказано отдельно.

История оставлена целиком намеренно: каждое из этих решений однажды уже
было сделано неправильно, и причина, по которой оно такое, дороже, чем
аккуратность текста.

**EXECUTE на новую функцию в Postgres по умолчанию выдан PUBLIC.** Поэтому
все 52 функции схемы `app` были вызываемы любым вошедшим агентом, а мои
`grant execute ... to service_role` не ограничивали ничего — доступ и так
был у всех. Измерено: обычный агент вызовом `app.expire_mandates()` погасил
4 мандата и **опустошил каталог** — опубликованных объектов было 3, стало 0.

Закрыто в `0025`: снят дефолтный PUBLIC, права выданы явно (19 функций
агенту вместо 52), и у двух опасных функций появилась проверка внутри — на
случай возврата гранта. Для функций, которые админ может законно запускать
руками, грант открыт роли `authenticated`, а админа от агента отличает
проверка **внутри** функции: роль в Postgres одна на всех вошедших.

**Публичный каталог был сломан для анонимов, и тесты этого не видели.**
Политика `objects_read` вызывала `app.current_agent_id()`, а анониму ни
`USAGE` на схему `app`, ни `EXECUTE` миграциями не выдавались. Анонимное
чтение падало с `permission denied for function current_agent_id`. Тесты
проходили только потому, что **харнесс выдавал анониму права, которых в
продакшене нет** — он делал тестовое окружение свободнее реального и
маскировал настоящие границы.

Лечение не грантом, а разделением политики: условие для анонима больше не
содержит вызова функций вовсе, поэтому каталог не может сломаться из-за
прав на схему `app`. Закреплено тестом, который проверяет, что у анонима
`USAGE` на `app` нет — и каталог всё равно читается.

**Очередь напоминаний, а не отправка на месте.** В Postgres здесь нет ни
`pg_net`, ни `http`, поэтому исходящий запрос из базы сделать нечем. Но
разделение полезно и само по себе: база решает, что и кому напомнить, — это
проверяемо тестами; Next.js отправляет — это нет. Плюс `unique (activity_id,
kind)`, статус `sending` при выдаче и счётчик попыток: расписание может
сработать повторно, маршрут — упасть на середине, и без этого агент получил
бы одно и то же несколько раз.

**Связь объекта с собственником — основание доступа, а не пометка.**
`can_see_contact()` для участников сделки опирается именно на
`object_ownerships`. Измерено: снятие связи при открытой сделке отбирало у
closing-агента телефон собственника — видел 1, стало 0, — **а сделка шла
дальше** в статусе «аванс». Причём сделать это мог другой участник
в одиночку.

Правило поэтому узкое: пока по объекту идёт сделка, он **не может остаться
без собственника**. Добавлять собственников при этом можно свободно — это
только расширяет доступ. Исправить ошибочно указанного собственника
по-прежнему можно: сначала добавить верного, потом снять неверного, и
объект ни на миг не остаётся без стороны. Без сделки объект можно оставить
и без собственника: это записанный лид, и `create_object()` такое допускает.

**Сумма долей по объекту не выходит за единицу.** Было 2.6 — ничто не
держало сто процентов. Это межстрочное правило, поэтому триггер, а не
`CHECK`: `CHECK` видит только свою строку. Пустая доля означает «неизвестна»
и в сумму не идёт.

**Смена роли в собственности — это перенос, а не правка поля.** Роль входит
в составной ключ `(object_id, contact_id, role)`, поэтому наивный `UPDATE`
оставлял бы у человека две роли по одному объекту вместо одной изменённой.
`set_object_ownership()` это скрывает; структурные колонки `object_id` и
`contact_id` закрыты, так что переподвязать связь к другому объекту нельзя —
только снять и завести заново, и тогда оба действия видны в журнале
по отдельности.

**Порядок шагов в `merge_contacts()` — не стиль, а защита от потери данных.**
Ссылки на контакт устроены так:

```
requirements.contact_id      ON DELETE CASCADE   ← удаление уничтожит потребности
contact_phones.contact_id    ON DELETE CASCADE   ← и телефоны
object_ownerships.contact_id ON DELETE RESTRICT  ← удалить не даст вовсе
```

Поэтому лишняя запись удаляется **последней**, когда с неё уже всё снято.
Измерено: если переставить удаление в начало и у записи **нет** связей с
объектами, `RESTRICT` молчит, и потребность исчезает **без единой ошибки** —
было 1, осталось 0. Если связи есть, неправильный порядок упирается в
`RESTRICT`, то есть ловится случайно; поэтому в тестах есть отдельный случай
записи без связей, который проверяет порядок сам по себе.

Обрабатываются и два уникальных индекса: `contact_phones_one_primary_idx`
(один основной номер на контакт) и `object_ownerships_pkey`
(объект + контакт + роль) — если обе записи указаны собственниками одного
объекта в одной роли, лишняя связь убирается, а не обходится.

**Объединять можно только свои записи — обе.** Иначе объединение становится
способом забрать чужого клиента: приписал к своей записи — и он твой,
вместе с телефоном и потребностями. Дубликат на двух агентов сначала
передаётся одному через `transfer_contact()` либо склеивается админом.

При объединении **роли складываются** — в этом и смысл правила «роли это
флаги одной записи». Пустые поля остающейся записи заполняются из
присоединяемой, заметки склеиваются с пометкой, откуда взялось: терять
написанное человеком незачем. Ведущий агент потребности не меняется, поэтому
инвариант `0018` не затронут и подборы двигать не нужно.

**«Один человек — одна запись» теперь действительно держится схемой.**
Это правило из задания, и схема его не держала: проверка показала, что два
контакта с телефоном `+996700111222` уживались свободно, а тот же номер в
виде `0700 11 12 22` давал **третью** запись того же человека.

Второе важнее первого: простой `unique` по тексту телефона обходится
форматированием, и такое ограничение **хуже отсутствующего** — создаёт
уверенность, которой нет. Поэтому есть `app.normalize_phone()`, которая
сводит `+996700111222`, `0700 11 12 22`, `700111222` и
`+996 (700) 11-12-22` к одному значению, генерируемая колонка
`phone_normalized` и глобальный уникальный индекс по ней. Иностранные
номера остаются цифрами: их план нумерации мы не угадываем.

Компромисс: номер, которым реально пользуются двое, придётся записать
одному контакту. На этом правиле держится смысл `roles[]` — роли это флаги
одной записи, а не повод завести вторую.

**Поиск по телефону перед созданием, и что он отдаёт.** Без поиска правило
только наказывало бы за дубликат: агент узнавал бы о существующей записи из
ошибки сохранения. Но здесь сталкиваются два правила — «одна запись»
требует сказать, что контакт есть, а инвариант 4 чужие контакты закрывает.
`find_contact_by_phone()` отдаёт минимум, который решает задачу: факт
существования и **имя коллеги**, у которого контакт. Имя самого контакта и
ссылку — только если инвариант 4 их и так открывает. Агент уже держит этот
номер в руках, он его и ввёл, поэтому узнаёт ровно одно: с человеком
работает такой-то коллега, надо договориться.

**Роль контакта НЕ обязательна, и это осознанно.** Здесь я поставил
ограничение `check (array_length(roles, 1) >= 1)` и оно оказалось неверным
дважды. Во-первых, оно ничего не проверяло: `array_length('{}', 1)` даёт
`NULL`, `NULL >= 1` тоже `NULL`, а `CHECK` при `NULL` считается
выполненным — контакт без ролей проходил беспрепятственно. Во-вторых, его
не должно быть и в рабочем виде: «контактное лицо» и «доверенное лицо» это
роли **связи** (`object_ownerships.role`), а не контакта, и человек, который
всего лишь контактное лицо по объекту, ни одной роли контакта не имеет.
Запрет закрыл бы случай из самого задания. В списке такой контакт помечен
как «роль не указана».

**Телефоны вынесены в отдельную таблицу `contact_phones`.** RLS в Postgres
построчный, не поколоночный. Телефон в `contacts.phones[]` невозможно
закрыть, оставив контакт открытым: политика либо отдаёт строку целиком, либо
не отдаёт. Это несущая конструкция инварианта 4, а не декоративное разбиение.

**`object_ownerships` закрыта тем же предикатом, что контакты.** Иначе
инвариант 4 обходился бы одним join: таблица связи выдала бы `contact_id`.

**Представления кабинета не присоединяют контакты внутренним join-ом.**
В карточках это LEFT JOIN, в списках — подзапрос. Агент, которому контакт
не положен, видит строку с пустым именем, а не теряет её целиком. Это ровно
«объект, условия и комиссия да, контакт нет».

Цена ошибки здесь измерена: если в `object_list_v` заменить подзапрос
собственников на обычный join, посторонний агент видит **0 объектов из 3** —
RLS скрывает контакты, и внутреннее соединение выбрасывает строки целиком.
Это проверяется мутацией в `inv11_list_views`. Подзапрос нужен ещё и потому,
что у объекта бывает несколько собственников, и join размножил бы строку
объекта.

**Передача клиента переносит работу целиком, а не одну колонку.** Переезжают
контакт, его открытые потребности и подборы по ним. Это следствие инварианта,
а не удобство: `0018` сделала `matches.closing_agent_id` производным от
агента потребности, и проверка показала, что если передвинуть
`requirements.agent_id`, не двинув подборы, инвариант остаётся нарушенным на
существующих строках — триггер на `matches` при правке `requirements` не
срабатывает, и расхождение живёт молча.

Закрытые потребности и отвал остаются за тем, кто их вёл: это уже сделанная
работа, и подборы по ним тоже не двигаются, поэтому инвариант на них цел.

**Передача отказывает при незавершённых сделках**, называя объекты, которые
мешают. Тоже следствие, а не осторожность: агенты сделки заморожены в её
строке, и если подбор уедет к другому, `check_deal_from_match()` перестанет
пропускать правки — проверено, `close_deal()` падал с `INVARIANT_3`, сделка
становилась незакрываемой. Комиссия по идущей сделке принадлежит тем, кто её
ведёт, поэтому передача её не переписывает.

**Передача объекта двигает и listing-агента активного мандата**, то есть
долю listing в комиссии: по инварианту 3 она идёт из мандата.

**«В сделке» означает существующую сделку.** Статус подбора `in_deal` можно
было поставить прямым запросом при нуле сделок: политика `matches_update`
разрешает правку closing-агенту, а PostgREST отдаёт таблицу напрямую. Подбор
начинал врать — заявлял сделку, которой нет, и в списке сделок её не было.
Держит триггер `c_match_in_deal_requires_deal`, а не проверка в функции,
именно потому, что прямой `PATCH /matches` функцию не трогает. Обратное
правило там же: пока сделка жива, подбор из `in_deal` не уводят, иначе
сделка висела бы на подборе, который её отрицает.

Отказ требует причины, показ — даты: «назначен показ» без даты это не
назначенный показ. При выходе из отказа причина очищается — она относилась
к прошлому решению.

**SECURITY DEFINER обходит RLS, поэтому проверка прав обязана быть внутри
функции.** Функции из `0007` были объявлены `SECURITY DEFINER` без
собственных проверок, и на схеме до `0016` посторонний агент мог:

| Что мог сделать посторонний агент | Последствие |
|---|---|
| `close_deal(чужая сделка, любая цена)` | Закрыть чужую сделку и зафиксировать комиссию. Проверено: закрыл по цене 999 000, записана комиссия 19 980, мандат и потребность закрыты |
| `withdraw_object(чужой объект)` | Снять чужой объект с публикации |
| `create_match(объект, чужая потребность)` | Назначить **себя** closing-агентом на чужого клиента — захват половины комиссии |

Политики RLS от этого не защищали и не могли: `SECURITY DEFINER` их обходит
by design. Третий пункт исправлен не проверкой, а изменением логики:
`closing_agent` теперь берётся **из потребности**, а не из того, кто нажал.
Предлагать объект чужому клиенту по-прежнему можно и это полезно, но доля
closing-агента идёт тому, кто ведёт клиента (инвариант 3). Все три случая
закрыты регрессией в `inv13_deal_access`.

**Заключить договор может любой агент, если активного нет.** Здесь я сначала
поставил проверку «только тот, кто завёл объект», и она оказалась неверной:
объект в базу внёс один агент, а договор с собственником есть у другого — при
строгой проверке второй не может его оформить, и объект остаётся
непубликуемым. Заключение договора это принесённая работа, а не действие над
чужой. Остаточный риск признаю: агент может оформить договор на чужой объект
и получить половину комиссии. Он виден в журнале и обратим админом, а запрет
ломал бы честный случай каждый раз. Публикация, снятие и подтверждение
актуальности остаются строгими — это действия над объектом, который уже
кому-то принадлежит.

**Этапы сделки и её завершение — разные функции.** `set_deal_status()` водит
сделку по этапам аванс → документы → подписание → расчёт, но `closed` и
`failed` отклоняет: закрытие требует финальной цены, от которой считается и
фиксируется комиссия, а срыв — причины. Иначе сделку можно было бы «закрыть»
без цены, и комиссия осталась бы непосчитанной.

**Объект, собственник и мандат создаются одной транзакцией** —
`create_object()`. Объект без мандата опубликовать нельзя (инвариант 1),
поэтому цепочка «создали объект, потом мандат, потом связь с собственником»
на любой оборванной середине оставляет объект, с которым нельзя работать.
Проверяется тестом: при мандате с истёкшим сроком не остаётся ни объекта,
ни осиротевшего контакта собственника.

Объект всегда создаётся **черновиком**. Публикация — отдельный шаг, и он
требует мандата; форма это прямо говорит и позволяет завести объект без
договора сознательно.

**Править объект может тот, кто его завёл, listing-агент активного мандата
и админ.** В `0006` это мог любой одобренный агент — политика проверяла
только `app.current_agent_id() is not null`. Пока правки шли через SQL, это
было терпимо; с появлением формы это значило бы, что любой агент молча
переписывает цены и фото в чужих объектах. РЕШЕНИЕ ОБРАТИМО: если в
агентстве правят объекты сообща, политику можно вернуть к прежнему виду.

Защита в два слоя, и это не избыточность: `update_object()` проверяет право
сама, но PostgREST отдаёт таблицы напрямую, поэтому агент может послать
`PATCH /objects` мимо функции — там держит политика. Тесты проверяют оба
слоя отдельно, потому что мутация, ослабляющая только политику, через
функцию не видна.

**Статус «в сделке» вручную не ставится.** Он означает, что по подбору
создана сделка, и приходит из `create_deal_from_match()` (инвариант 2).
Иначе потребность показывала бы сделку, которой нет. Остальные статусы,
включая «закрыта» и «отвал», ставятся руками: клиент мог купить сам.

**Фильтры списков живут в URL, а не в состоянии компонента.** Ссылку на
отфильтрованный список можно отправить коллеге, а перезагрузка страницы не
сбрасывает подбор условий. Значения фильтров проверяются по белому списку
(`lib/list-params.ts`), поэтому подставить в запрос произвольное значение
через строку запроса нельзя.

**Активность приватна по умолчанию, но автор может поделиться.** Прежде
активности были видны только автору и админу — это было строже задания, и
обоснованно: заметка «звонил, +996…» обошла бы инвариант 4. Проверка
показала цену такой строгости: listing-агент видел **ноль** активностей
коллеги по своему объекту. Показ записан, а согласовать его нечем, и CRM
превращается в личный блокнот.

Поэтому у активности появился флаг `is_shared`. По умолчанию ложь. Аудитория
общей записи **узкая** — не «все агенты», а только тот, кто может
действовать по этой сущности: `can_edit_object` для объекта,
`can_lead_match` для подбора, `is_deal_party` для сделки, агент
потребности, owner_agent контакта. Свои записи видны всегда, чужие приватные
не видны никому кроме админа.

**Остаточный риск признаю.** Если автор напишет в общую заметку телефон
клиента и поделится ею на объекте, его прочтёт listing-агент объекта — а
инвариант 4 телефон клиента ему не даёт, пока нет активной сделки. Защита
здесь человеческая: приватно по умолчанию, узкая аудитория и прямое
предупреждение в форме ровно в момент, когда ставится галочка. Полностью
убрать риск можно только запретив делиться — и тогда согласовать показ в
системе будет нечем. Если в агентстве это неприемлемо, флаг убирается одной
правкой политики.

**`done` и `done_at` не расходятся.** Проверка нашла два принимавшихся
состояния: `done = true` без даты выполнения и дата выполнения в 2027 году
при `done = false`. Теперь дату ведёт триггер: отметили — зафиксировал,
сняли — стёр, будущую прижал к настоящему. Клиенту колонка `done_at` не
выдана вовсе.

**Свою строку агент видит при любом статусе** — политика
`agents_read_self` (`0013`). До неё `agents_read` требовала одобренного
агента, и неодобренный не видел даже себя. Следствие было не только про
чтение: Postgres применяет SELECT-политику при поиске строк для `UPDATE`,
поэтому `update agents set full_name = … where auth_user_id = auth.uid()`
у неодобренного задевал 0 строк — молча, без ошибки. Получался замкнутый
круг: админ видел заявку с почтой вместо имени, а человек не мог вписать
имя, пока его не одобрят.

Политики складываются по OR, поэтому это только расширение: одобренные
как и раньше видят всех, остальные — ровно себя. Заблокированному это тоже
нужно, иначе кабинет не может сказать, что доступ отозван, и показывает
общий экран ожидания. Форма имени доступна прямо на экране ожидания.

**Агент не может сам себя одобрить и повысить.** В `0006` политика
`agents_self_update` разрешала правку собственной строки, а грант был выдан
на таблицу целиком. Вместе это позволяло любому агенту выполнить
`update agents set status='approved', role='admin' where auth_user_id = auth.uid()`
и стать админом — проверено на схеме до `0011`, проходило. Закрыто двумя
независимыми способами: поколоночный грант (агенту выдано только
`full_name` и `phone`) и триггер `b_guard_agent_privileges`, который держит
правило даже если грант вернёт неосторожная миграция. Статус и роль меняются
только через `app.approve_agent()`, `app.block_agent()` и
`app.set_agent_role()`, и каждая проверяет админа сама.

Прямой доступ к базе правило обходит сознательно — условие
`auth.uid() is not null` в триггере. Иначе первого админа было бы не завести.

**Последнего админа нельзя заблокировать или разжаловать** —
`app.assert_admin_remains()`. Иначе систему можно запереть так, что одобрять
новых агентов станет некому.

**Функции кабинета лежат в `public`, а не в `app`.** PostgREST отдаёт `rpc`
только из открытых схем, поэтому `app.ensure_agent()` из кабинета был бы
недоступен. В `0012` добавлены пустые обёртки в `public`; схему `app` целиком
не открываем, чтобы наружу не смотрели `app.write_audit()`,
`app.can_see_contact()` и прочие внутренности. Проверяется тестом
`inv9_public_api` — ошибка, которую иначе поймал бы только живой прогон.

**Вход через Telegram не делается, якорь инварианта 6 — `auth_user_id`.**
Решено отдельно. Суть инварианта не изменилась: один человек — один аккаунт,
повторный вход не создаёт дубликат и не теряет владение объектами. Изменилось
то, чем он закреплён: вместо Telegram-идентичности это идентичность Supabase
Auth, и вход идёт через `app.ensure_agent()` — upsert по `auth.uid()`.
`telegram_id` стал необязательным, но остался уникальным: агентов без Telegram
может быть сколько угодно (NULL уникальности не нарушает), а два аккаунта на
один Telegram — по-прежнему нельзя.

Авторизацию это не задело вовсе: `app.current_agent_id()` и `app.is_admin()`
с самого начала опознают агента по `agents.auth_user_id = auth.uid()`, поэтому
инвариант 4, гейт «CRM только одобренным» и все политики RLS работают как
работали, с любым способом входа в Supabase Auth.

Вместе с этим появилось ограничение `agents_has_identity`: у агента обязана
быть хотя бы одна идентичность. Без него инвариант 6 получил бы дыру — строка
без `auth_user_id` и без `telegram_id` ни с каким входом не сопоставляется, но
владеть контактами и объектами может. Человек потом логинится, получает новую
строку, а объекты остаются за мёртвой. Это ровно та потеря владения, которую
инвариант 6 запрещает. Если вам нужно заводить агентов заранее, без всякой
идентичности, это ограничение придётся снимать осознанно.

**Перенос даёт мандат `active` + `contract_confirmed = false`**, а не
отдельный статус «требует подтверждения». Согласовано отдельно: иначе
инвариант 1 снял бы с публикации все переносимые объекты. Флаг уже есть в
модели мандата и означает ровно это.

**`app.expire_mandates()` вызывается по расписанию pg_cron** — миграция
`0009_schedule.sql`, ежедневно в 00:10 UTC (06:10 по Бишкеку, до начала
рабочего дня). Это единственное место, где инвариант 1 зависит от чего-то
вне базы, поэтому миграция устроена так:

- если `pg_cron` недоступен, она **не падает**, а выдаёт `WARNING`. Падение
  заблокировало бы всю цепочку миграций на свежем проекте Supabase, где
  расширение ещё не включено в панели;
- проверить, что расписание реально стоит, можно запросом
  `select * from app.schedule_health()`. Он показывает три вещи: установлен
  ли `pg_cron`, активно ли задание и нет ли уже просроченных активных
  мандатов — последнее и есть симптом неработающего расписания.

**После развёртывания запустить `app.schedule_health()` обязательно.** Молча
незапланированное истечение мандатов — худший из вариантов: инвариант 1
выглядит рабочим, а объекты висят в каталоге с просроченными договорами.

**Комиссия не выносится в публичную часть.** Витрина не содержит ни
комиссии, ни внутреннего состояния, а из полей агента — только три
открытых сознательно (имя, стаж, подтверждённый номер в реестре).
Проверяется прогоном, а в Postgres это держали отозванные у роли `anon`
представления `deal_commission_v` и `match_commission_v`.

## Слой доступа

Весь путь к базе идёт через `lib/db`. Не по соглашению, а физически: до D1
достаёт только Worker, а в Worker'е привязка доступна только отсюда.

| Модуль | За что отвечает |
|---|---|
| `sql.ts` | привязка, батчи-транзакции, время, идентификаторы |
| `visibility.ts` | предикаты видимости: контакт, объект, сделка |
| `session.ts` | кто вошёл; `requireAgent()`, `requireAdmin()` |
| `login.ts` | вход по ссылке: одноразовые токены, сессии |
| `email.ts` | отправка писем привязкой Cloudflare |
| `access.ts` | `canSeeContact()`, `canEditObject()` |
| `audit.ts` | журнал; запись едет батчем с правкой |
| `commission.ts` | комиссия на целых числах |
| `objects.ts` | объекты, `stampTimestamps()`, передача |
| `mandates.ts` | мандаты, `releaseStmts()`, истечение |
| `contacts.ts` | контакты, телефоны, объединение, доли |
| `requirements.ts` | потребности |
| `matches.ts` | подборы |
| `deals.ts` | сделки, закрытие, срыв |
| `activities.ts` | звонки, показы, задачи |
| `notifications.ts` | очередь напоминаний |
| `leads.ts` | заявки по объекту |
| `requests.ts` | заявки «подберите мне» |
| `agents.ts` | агенты и агентства |
| `catalog.ts` | витрина: состав публичной выдачи |
| `cabinet.ts` | списки и карточки кабинета |
| `invites.ts` | выдача ссылки-приглашения админом |

Три правила, из которых следует остальное:

1. **Запись в журнал едет тем же батчем, что и правка.** Батч D1 —
   транзакция, значит изменение без журнальной записи не сохранится в
   принципе. Отдельный вызов после правки такого свойства не даёт.
2. **Предикат видимости — один на всех.** Двадцать запросов зовут три
   функции. Повторённое двадцать раз условие однажды забудут в одном месте.
3. **Стороны комиссии не принимаются аргументами.** listing-агент берётся
   из мандата, closing — из подбора. Передать их снаружи означало бы дать
   выписать комиссию на себя.

## Что НЕ сделано

- **Вход не проверен на живой почте.** Проверено всё до границы отправки:
  одноразовость ссылки, срок, одинаковые ответы на неизвестную и известную
  почту, запрет открытого перенаправления, отказ заблокированному. Само
  письмо в этой сессии отправить было некуда — домен завели позже.
- **На бесплатном плане Workers письма уходят только на подтверждённые
  адреса.** Для ЗАВЕДЕНИЯ агента это обойдено приглашением по ссылке (см.
  раздел про вход). Для ПОВТОРНОГО входа — нет: сессия живёт тридцать
  дней, и когда она истечёт, агент запросит ссылку сам, а письмо не
  дойдёт. Выдавать ссылку заново придётся админу. Снимается платным
  планом.
- **Сжатие снимков делает браузер, а не сервер.** Преобразование изображений
  у Cloudflare — платная услуга, на этом плане её не включить
  (`image_resizing: off`, `editable: false`), а в Worker'е нет библиотеки
  изображений. Браузер без `OffscreenCanvas` отправит снимок как есть и без
  миниатюры: в карточке отдастся полный снимок — медленнее, но не сломано.
  Такие пробелы закрывает пересчёт (ниже), и он тоже идёт в браузере:
  фонового задания на сервере быть не может по той же причине. Значит
  вкладку надо держать открытой, и автоматически это не случится — кто-то
  должен нажать кнопку.
- **Объединение контактов необратимо.** Присоединённая запись удаляется,
  кнопки «вернуть» нет, старые ссылки на неё дают 404. Содержимое
  остаётся в журнале — и теперь это ПРАВДА: до 27 ноября 2026 там лежало
  одно имя, хотя этот абзац обещал содержимое. Собрать запись по имени
  нельзя, поэтому в журнал пишется всё, из чего она состоит (см. раздел
  про объединение ниже). Автоматической отмены всё равно нет: восстановить
  можно руками, по журналу.
- **Дубликаты ищутся по имени, но не по телефону и не по адресу.** Имя
  сравнивается с учётом регистра и инициалов (ниже), а вот два контакта с
  похожими, но не совпадающими номерами в кандидаты не попадут. Полное
  совпадение номера невозможно: один номер — одна запись держится схемой.
- **Напоминания только в Telegram.** Почта как канал не реализована.
  Очередь к этому готова — у записи есть поле канала, нужен отправщик.
- **Коннекторов к lalafo и house.kg нет, есть фид.** Открытой документации
  по выгрузке нет ни у одной из площадок: ни описания API, ни требований к
  файлу — искал и в сети, и на самих сайтах. lalafo вдобавок отвечает 403
  автоматическим клиентам, то есть блокирует их на своей стороне. Писать
  коннектор к неизвестному формату значило бы получить код, который
  выглядит готовым и рассыпается при первой встрече с площадкой. Вместо
  этого `/feed.xml` (ниже). Таблица `publication_channels` по-прежнему
  описывает состояние, и заполнять её некому.
- **Коммерческая недвижимость в фид не попадает.** В справочнике YRL она
  описывается другим набором полей, а точного значения проверить не
  удалось. Значение нужно уточнить по справке и дописать в `CATEGORY` в
  `lib/feed.ts`. Выдуманное значение сделало бы невалидным весь файл, а не
  одно объявление, поэтому пока не дописано.

  Зацепка, НЕ проверенная по первоисточнику: поиск по сети говорит, что
  для коммерческих объявлений `<category>` принимает единственное значение
  `коммерческая`/`commercial`, а вид назначения задаётся отдельным
  элементом `<commercial-type>`. Это пересказ, а не справка: часть выдачи
  относилась к требованиям для новостроек. Официальная страница —
  `yandex.ru/support/realty/ru/requirements/requirements-commercial.html`;
  хост в окружение добавлен 27 ноября 2026, но саму страницу в этой сессии
  прочитать не дали. Пока значение не прочитано своими глазами, в
  `CATEGORY` оно не идёт.

  **Кабинет об этом предупреждает.** На карточке опубликованного объекта,
  который в выгрузку не попадает, стоит строка об этом: молчание хуже
  отказа — агент считал объявление размещённым. Условие спрашивается у
  самой выгрузки (`inFeed` из `lib/feed.ts`), а не повторяет её список
  видов. Проверено мутацией: дай `inFeed` свой список — падает «кабинет
  знает, что коммерческий в выгрузку не идёт».
- **В контакте фида только телефон и название.** У контакта в YRL есть и
  другие поля со списком допустимых значений, но проверить их не удалось —
  справка Яндекса закрыта сетевой политикой окружения.
- **Карточка агента с галочкой реестра вживую не проверена.** На живом
  сайте проверен случай «номер заявлен, но не подтверждён»: витрина его не
  отдаёт вовсе — проверено поиском по всему ответу страницы. Имя, аватарка
  и подпись на четырёх языках тоже проверены. Полный вид — со стажем и
  отметкой «номер сверен администратором» — требует записи в учётную
  запись агента, и этот запрос из сеанса отклонил классификатор. Делается
  настоящим путём: год в профиле, «Подтвердить» в списке агентов у админа.
- **Данных в базе нет.** Переносить было нечего: в Supabase на момент
  переезда лежало 0 объектов, 0 мандатов и 1 агент. Миграция данных не
  писалась и не понадобилась. Сам проект Supabase удалён 26 ноября 2026
  вместе с тремя ключами, лежавшими в переменных Worker; среди них был
  `SUPABASE_SERVICE_ROLE_KEY`, дававший полный доступ в обход правил.
  Удаление проекта и обезвредило его: базы, к которой он вёл, больше нет.
