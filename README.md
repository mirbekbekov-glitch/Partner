# Платформа профессионалов — модель данных и серверные инварианты

Платформа аренды и продажи недвижимости в Бишкеке. Публичный каталог открыт
всем, CRM живёт внутри кабинета агента и открывается только агентам со
статусом «одобрен». Сайт и CRM — один продукт и одна база: **публикация
объекта это его состояние, а не выгрузка во вторую систему.**

Этот этап закрывает модель данных и серверные инварианты. UI минимальный.

## Состояние репозитория

Репозиторий был пуст, поэтому проект создан с нуля. Готово и проверено:
схема, инварианты, слой доступа, тесты и минимальный UI кабинета
(Next.js App Router + Supabase).

## Запуск кабинета

```bash
cp .env.example .env.local   # вписать URL проекта и anon key
npm install
npm run dev
```

### Обязательная настройка Supabase для входа

Вход сделан по ссылке на почту через `/auth/confirm`, и **без двух настроек
в панели Supabase он не заработает**:

1. **Authentication → URL Configuration → Redirect URLs** — добавить
   `http://localhost:3000/auth/confirm` и адрес продакшена.
2. **Authentication → Email Templates → Magic Link** — заменить тело на
   ссылку с `TokenHash`, иначе Supabase пришлёт ссылку на свой
   `/verify`, а наш маршрут её не получит:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email">Войти в кабинет</a>
```

### Первый админ

Пока админа нет, одобрять агентов некому. Первого заводят прямым доступом
к базе — триггер это пропускает сознательно, потому что сессии там нет:

```sql
update agents set role = 'admin', status = 'approved' where email = 'you@example.kg';
```

## Прогон тестов

Нужен локальный PostgreSQL 16. Сервер поднимается так:

```bash
PGDATA=/var/lib/postgresql/partner-test
/usr/lib/postgresql/16/bin/initdb -D "$PGDATA" -A trust -U postgres
/usr/lib/postgresql/16/bin/pg_ctl -D "$PGDATA" -o '-p 55432 -k /tmp' -l "$PGDATA/log" start
```

Дальше:

```bash
./tests/run.sh
```

Каждый тест получает свою базу из шаблона, поэтому тесты не видят друг друга
и порядок запуска ничего не меняет.

## Инварианты и чем они держатся

Все проверки живут в базе. Это сознательно: PostgREST отдаёт таблицы
напрямую, поэтому проверка в UI защищает только UI.

| № | Инвариант | Механизм | Тест |
|---|---|---|---|
| 1 | Публикация только при активном мандате; не больше одного активного мандата на объект | `mandates_one_active_per_object_idx` (partial unique) + `c_objects_publication_requires_mandate` + `c_channels_require_mandate` + `d_mandate_release_withdraws_object` + `app.expire_mandates()` | `inv1_publication` |
| 2 | Сделка только из подбора; закрытие закрывает мандат и потребность | `deals.match_id NOT NULL` + `b_deal_from_match` + `e_deal_closed` | `inv2_deal_from_match` |
| 3 | Комиссия 50/50; продажа 2%, аренда 50% первого месяца; до закрытия индикативно | `app.commission_total()`, `app.commission_shares()`, `deal_commission_v`, `match_commission_v` | `inv3_commission` |
| 4 | Телефон виден owner_agent, агентам активной сделки, админу | `app.can_see_contact()` + политики на `contacts`, `contact_phones`, `object_ownerships` | `inv4_phone_visibility`, `inv4b_cabinet_views`, `inv4c_page_queries` |
| 5 | Правка цены/фото/подтверждение обновляет `actual_at`; `published_at` не меняется никогда | `a_object_timestamps` + `app.confirm_actual()` | `inv5_timestamps` |
| 6 | Один человек — один аккаунт; повторный вход не плодит дубликат и не теряет объекты | `agents.auth_user_id UNIQUE` + `agents_has_identity` CHECK + `app.ensure_agent()` | `inv6_one_account` |
| 7 | Каждое изменение в журнале: кто, что, когда | `app.write_audit()` на всех 11 таблицах | `inv7_audit` |

Тесты проверены мутациями: при снятом триггере публикации, при незакрывающемся
мандате, при открытом всем телефоне и при изменяемом `published_at`
соответствующие тесты падают. Суть не в том, что тесты зелёные, а в том, что
они краснеют, когда инвариант сломан.

## Решения, которые стоит знать

**Телефоны вынесены в отдельную таблицу `contact_phones`.** RLS в Postgres
построчный, не поколоночный. Телефон в `contacts.phones[]` невозможно
закрыть, оставив контакт открытым: политика либо отдаёт строку целиком, либо
не отдаёт. Это несущая конструкция инварианта 4, а не декоративное разбиение.

**`object_ownerships` закрыта тем же предикатом, что контакты.** Иначе
инвариант 4 обходился бы одним join: таблица связи выдала бы `contact_id`.

**Представления кабинета присоединяют контакты через LEFT JOIN.** Агент,
которому контакт не положен, видит строку подбора с пустым именем, а не
теряет её целиком. Это ровно «объект, условия и комиссия да, контакт нет».

**Активности видны автору и админу, а не всей команде.** Заметка «звонил,
+996…» обошла бы инвариант 4, будь она открыта. Это строже задания; если
команде нужна общая история, решение придётся ослаблять осознанно.

**Свою строку агент видит при любом статусе** — политика
`agents_read_self` (`0013`). До неё `agents_read` требовала одобренного
агента, и неодобренный не видел даже себя. Следствие было не только про
чтение: Postgres применяет SELECT-политику при поиске строк для `UPDATE`,
поэтому `update agents set full_name = … where auth_user_id = auth.uid()`
у неодобренного задевал 0 строк — молча, без ошибки. Получался замкнутый
круг: админ видел заявку с почтой вместо имени, а человек не мог вписать
имя, пока его не одобрят.

Политики складываются по OR, поэтому это только расширение: одобренные
как и раньше видят всех, остальные — ровно себя. Заблокированному это тоже
нужно, иначе кабинет не может сказать, что доступ отозван, и показывает
общий экран ожидания. Форма имени доступна прямо на экране ожидания.

**Агент не может сам себя одобрить и повысить.** В `0006` политика
`agents_self_update` разрешала правку собственной строки, а грант был выдан
на таблицу целиком. Вместе это позволяло любому агенту выполнить
`update agents set status='approved', role='admin' where auth_user_id = auth.uid()`
и стать админом — проверено на схеме до `0011`, проходило. Закрыто двумя
независимыми способами: поколоночный грант (агенту выдано только
`full_name` и `phone`) и триггер `b_guard_agent_privileges`, который держит
правило даже если грант вернёт неосторожная миграция. Статус и роль меняются
только через `app.approve_agent()`, `app.block_agent()` и
`app.set_agent_role()`, и каждая проверяет админа сама.

Прямой доступ к базе правило обходит сознательно — условие
`auth.uid() is not null` в триггере. Иначе первого админа было бы не завести.

**Последнего админа нельзя заблокировать или разжаловать** —
`app.assert_admin_remains()`. Иначе систему можно запереть так, что одобрять
новых агентов станет некому.

**Функции кабинета лежат в `public`, а не в `app`.** PostgREST отдаёт `rpc`
только из открытых схем, поэтому `app.ensure_agent()` из кабинета был бы
недоступен. В `0012` добавлены пустые обёртки в `public`; схему `app` целиком
не открываем, чтобы наружу не смотрели `app.write_audit()`,
`app.can_see_contact()` и прочие внутренности. Проверяется тестом
`inv9_public_api` — ошибка, которую иначе поймал бы только живой прогон.

**Вход через Telegram не делается, якорь инварианта 6 — `auth_user_id`.**
Решено отдельно. Суть инварианта не изменилась: один человек — один аккаунт,
повторный вход не создаёт дубликат и не теряет владение объектами. Изменилось
то, чем он закреплён: вместо Telegram-идентичности это идентичность Supabase
Auth, и вход идёт через `app.ensure_agent()` — upsert по `auth.uid()`.
`telegram_id` стал необязательным, но остался уникальным: агентов без Telegram
может быть сколько угодно (NULL уникальности не нарушает), а два аккаунта на
один Telegram — по-прежнему нельзя.

Авторизацию это не задело вовсе: `app.current_agent_id()` и `app.is_admin()`
с самого начала опознают агента по `agents.auth_user_id = auth.uid()`, поэтому
инвариант 4, гейт «CRM только одобренным» и все политики RLS работают как
работали, с любым способом входа в Supabase Auth.

Вместе с этим появилось ограничение `agents_has_identity`: у агента обязана
быть хотя бы одна идентичность. Без него инвариант 6 получил бы дыру — строка
без `auth_user_id` и без `telegram_id` ни с каким входом не сопоставляется, но
владеть контактами и объектами может. Человек потом логинится, получает новую
строку, а объекты остаются за мёртвой. Это ровно та потеря владения, которую
инвариант 6 запрещает. Если вам нужно заводить агентов заранее, без всякой
идентичности, это ограничение придётся снимать осознанно.

**Перенос даёт мандат `active` + `contract_confirmed = false`**, а не
отдельный статус «требует подтверждения». Согласовано отдельно: иначе
инвариант 1 снял бы с публикации все переносимые объекты. Флаг уже есть в
модели мандата и означает ровно это.

**`app.expire_mandates()` вызывается по расписанию pg_cron** — миграция
`0009_schedule.sql`, ежедневно в 00:10 UTC (06:10 по Бишкеку, до начала
рабочего дня). Это единственное место, где инвариант 1 зависит от чего-то
вне базы, поэтому миграция устроена так:

- если `pg_cron` недоступен, она **не падает**, а выдаёт `WARNING`. Падение
  заблокировало бы всю цепочку миграций на свежем проекте Supabase, где
  расширение ещё не включено в панели;
- проверить, что расписание реально стоит, можно запросом
  `select * from app.schedule_health()`. Он показывает три вещи: установлен
  ли `pg_cron`, активно ли задание и нет ли уже просроченных активных
  мандатов — последнее и есть симптом неработающего расписания.

**После развёртывания запустить `app.schedule_health()` обязательно.** Молча
незапланированное истечение мандатов — худший из вариантов: инвариант 1
выглядит рабочим, а объекты висят в каталоге с просроченными договорами.

**Комиссия не выносится в публичную часть.** `public_catalog_v` не содержит
ни комиссии, ни агентов, ни внутреннего состояния; `deal_commission_v` и
`match_commission_v` у роли `anon` отозваны. Проверяется в приёмке.

## Слой доступа

Кабинет должен ходить через эти функции, а не UPDATE-ами по таблицам.
Инварианты держатся и при прямом UPDATE, но через функции клиенту физически
нечего передать неправильно: стороны комиссии и мандат выводятся на сервере.

| Функция | Назначение |
|---|---|
| `ensure_agent(name)` | вход; upsert по `auth.uid()` — основной путь (инвариант 6) |
| `approve_agent(id)` / `block_agent(id)` | одобрение и блокировка, только админ |
| `set_agent_role(id, role)` | смена роли, только админ |
| `update_my_profile(name, phone)` | правка своего имени и телефона |
| `app.login_by_telegram(tg, name, auth_uid)` | вход, когда известен Telegram-id; upsert по `telegram_id` |
| `publish_object(id)` / `withdraw_object(id)` | публикация и снятие |
| `create_match(object_id, requirement_id)` | подбор; `closing_agent` = текущий агент |
| `create_deal_from_match(match_id)` | сделка; принимает ТОЛЬКО `match_id` |
| `close_deal(id, final_price)` / `fail_deal(id, reason)` | закрытие и срыв |
| `app.confirm_actual(object_id)` | подтверждение актуальности |
| `app.expire_mandates()` | истечение мандатов по дате, по расписанию |
| `app.backfill_missing_mandates()` | перенос: объекту без мандата — мандат |

## Что НЕ сделано

- **Вход и одобрение не проверены на живом Supabase.** Проверено: сборка,
  типы, что все вызываемые функции лежат в `public` и доступны роли
  `authenticated`, и что все запрашиваемые колонки существуют и отдаются под
  RLS. Но сам обмен письмами с Supabase Auth в этой сессии запустить было
  негде, поэтому настройку из раздела выше надо сделать и проверить руками.
- **Пароля нет, только ссылка на почту.** Сознательно: нет ни хранения
  пароля, ни восстановления, ни экранов смены. Если нужен пароль — это
  `signInWithPassword` плюс экран восстановления.
- **Публичного каталога как страниц нет** — только витрина
  `public_catalog_v`.
- **Страницы не проверены на живой Supabase.** Проверено: сборка, типы и то,
  что все запрашиваемые колонки существуют и отдаются под RLS
  (`inv4c_page_queries`). Запустить страницы против настоящего PostgREST
  в этой сессии было негде.
- Выгрузка в lalafo и house.kg: таблица `publication_channels` описывает
  состояние, сами коннекторы не писались.
- Списки объектов и потребностей: есть только карточки по id.
- Ничего не задеплоено и не опубликовано.
